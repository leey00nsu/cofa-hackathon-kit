# 요구사항

공식 과제 README의 필수조건을 먼저 기록한다. 프로젝트 AGENTS의 Evidence 규칙에 따라 실제 고객 질문·답변 원문은 `.hackathon/private/INTERVIEWS.md`에 Q번호로 보관하고 이 장부에는 요약·참조만 남긴다. 사실·가설·반박을 구분한다.

요구사항과 성공 조건은 비개발자도 이해하도록 사용자 행동과 눈으로 확인할 수 있는 결과로 쓴다. 파일·명령·ID는 해당 근거 칸에 보존하고, 고객 확인과 자체 선택·미확인을 구분한다.

## 탐색 범위

INTERVIEW_PROTOCOL.md에 따라 매 답변마다 갱신한다. 상태는 확인·부분확인·미확인·해당없음이다. 질문하지 않은 영역은 미확인이다. 해당없음도 확인된 범위에 근거해야 한다.

| 영역 | 상태 | 답변 Q/공식 과제 근거 | 남은 질문과 구현 영향 |
| --- | --- | --- | --- |
| 현재 업무 흐름 | 미확인 | — | 실제 한 건의 시작부터 완료까지 확인 |
| 입력과 결과 | 미확인 | — | 자료와 결과·남겨야 할 기록 확인 |
| 판단 기준 | 미확인 | — | 처리 대상·제외·경계 조건 확인 |
| 사람의 판단과 권한 | 미확인 | — | 사람의 확인·자동 행동·금지 행동 확인 |

| 우선순위와 성공 | 미확인 | — | 필수·후순위·관찰 가능한 성공 확인 |

## 요구사항 목록

우선순위는 P0/P1/P2 또는 미확인으로 둔다. 고객의 편의 제안을 임의로 필수조건으로 올리지 않는다.

상태는 Proposed / Confirmed / Implemented / Verified / Blocked를 사용한다. 일부 구현·일부 검증은 남은 항목과 함께 적고 전체 수락 조건의 실행 근거가 없으면 Verified로 올리지 않는다. D/V 번호는 기존 DECISIONS/VERIFICATION의 상세 기록을 가리킨다.

실제 결과 셀에는 관찰 요약과 `check:<실제 실행ID>` 또는 `manual:<실제 관찰ID>`를 남긴다. 검사는 `--requirement <R번호>`로 연결한다. 구현 파일은 작업 공간 상대 경로이며 함수/행 참조를 덧붙일 수 있다. audit-requirements는 이 표를 읽기만 하며 미실행·오래된 근거·누락을 확인한다. 감사 PASS가 전체 요구 충족을 뜻하지 않는다.

UI 수락 조건이 남은 경우 Implemented + 자동 검사 결과 + ‘최종 UI 확인 대기’로 기록하고 다음 독립 구현을 진행한다. 중간의 자동 검증을 참가자 클릭 테스트로 대체하지 않는다. 모든 R에 불필요한 수동 UI 조건을 추가하지 않는다.

| ID | 요구사항 | 상태 | 우선순위·근거 | 고객 근거 Q/공식 과제 위치 | 관찰 가능한 수락 조건 | 설계 D | 실제 구현 파일 | 검증 절차 V/명령·테스트 | 실제 결과·실행 기록 | 남은 질문·문제 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

## 구현 진입 판단

아직 판단하지 않음. 선택한 첫 흐름, 수락 기준의 근거, 관련 중요한 미확인, 독립적으로 구현 가능한 범위를 기록한다. 추가 질문이 없다면 그 이유를 설명한다.

## 고객 대화 참조

아직 대화하지 않음. 실제 답변을 받은 뒤 Q번호·짧은 요약·`.hackathon/private/INTERVIEWS.md`의 해당 위치를 연결한다. 고객 원문은 여기 복사하지 않고 작업 공간 안의 Git 제외 영역에만 보관한다. 외부로 전송하지 않는다.
