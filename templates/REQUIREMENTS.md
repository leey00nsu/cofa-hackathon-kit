# 요구사항

공식 과제 README의 필수조건을 먼저 기록한다. 프로젝트 AGENTS의 Evidence 규칙에 따라 실제 고객 질문·답변 원문은 `.hackathon/private/INTERVIEWS.md`에 Q번호로 보관하고 이 장부에는 요약·참조만 남긴다. 사실·가설·반박을 구분한다.

요구사항과 성공 조건은 비개발자도 이해하도록 사용자 행동과 눈으로 확인할 수 있는 결과로 쓴다. 파일·명령·ID는 해당 근거 칸에 보존하고, 고객 확인과 자체 선택·미확인을 구분한다.

자료가 있는 과제에서는 한 줄의 뜻·식별자·단위·기간·반복/누락 처리·비율의 대상·자료 연결 관계 중 필요한 것만 관련 R의 설명/근거/수락 조건에 연결한다. 파일에서 관찰한 값과 고객이 확인한 업무 기준을 구분하고, 미확인은 남은 질문에 둔다. 별도 자료 장부를 만들지 않는다.

## 문제와 첫 흐름 요약

아직 과제 요약 없음. 첫 구현 전에 받은 자료·답변에서 아는 만큼 짧게 작성하고 중요한 변화만 갱신한다. 이 절이 핵심 PRD(무엇을 왜 만드는지 설명하는 문서)의 역할을 한다. 별도 PRD 파일·버전별 사본·중복 요구사항 표는 만들지 않는다. 기존 정본에 같은 설명이 있으면 위치를 참조한다.

- 해결할 문제·기대 효과: 미확인.
- 사용할 사람·사용 상황·현재 업무의 불편: 미확인.
- 주요 업무의 큰 흐름: 미확인. 입력 → 판단/처리 → 결과·업무 완료를 설명한다.
- 첫 구현 흐름(MVP)·관련 R: 미선정. 시작/끝과 대표 입력·기대 결과의 상세는 관련 R을 참조한다.
- 범위: 최종 필수 R / 첫 흐름에 포함할 R / 후순위·제외할 R과 근거를 구분한다. 아직 결정 없음.
- 중요한 미확인·제약: 관련 R의 근거·남은 질문과 공식 자료 위치를 참조한다. 아직 정리 없음.

상세 업무 규칙·수락 조건·진행 상태는 아래 R 행이 정본이다. 요약에는 관련 R/Q/D/V를 연결하고 같은 조건을 다시 쓰지 않는다. 업무 동작이나 수락 조건의 의미가 바뀌면 요약만 고치지 말고 해당 R도 함께 갱신해 기존 검증의 유효성을 확인한다. 검사기는 이 설명의 의미나 구현 준비 여부를 자동 판정하지 않는다.

## 요구사항 목록

우선순위는 P0/P1/P2 또는 미확인으로 둔다. 고객의 편의 제안을 임의로 필수조건으로 올리지 않는다.

상태는 Proposed / Confirmed / Implemented / Verified / Blocked를 사용한다. 일부 구현·일부 검증은 남은 항목과 함께 적고 전체 수락 조건의 실행 근거가 없으면 Verified로 올리지 않는다. D/V 번호는 기존 DECISIONS/VERIFICATION의 상세 기록을 가리킨다.

근거의 확실성(확인·가정·미확인), 이번 범위(포함·후순위·제외), 구현·검증 진행은 서로 다르다. 가정/미확인은 근거·남은 질문, 범위는 위 요약과 관련 결정, 진행은 기존 상태 칸에 둔다. 확인된 요구를 첫 흐름에서 미뤘다고 미확정으로 바꾸거나 ‘제외’를 새 진행 상태로 넣지 않는다. 공식 필수 요구는 MVP에서 뒤로 미뤄도 최종 필수로 남기며 못 마치면 미완료로 보고한다.

실제 결과 셀에는 관찰 요약과 `check:<실제 실행ID>` 또는 `manual:<실제 관찰ID>`를 남긴다. 검사는 `--requirement <R번호>`로 연결한다. 구현 파일은 작업 공간 상대 경로이며 함수/행 참조를 덧붙일 수 있다. audit-requirements는 이 표를 읽기만 하며 미실행·오래된 근거·누락을 확인한다. 감사 PASS가 전체 요구 충족을 뜻하지 않는다.

UI 수락 조건이 남은 경우 Implemented + 자동 검사 결과 + ‘최종 UI 확인 대기’로 기록하고 다음 독립 구현을 진행한다. 중간의 자동 검증을 참가자 클릭 테스트로 대체하지 않는다. 모든 R에 불필요한 수동 UI 조건을 추가하지 않는다.

## 구현 진입 판단

아직 판단하지 않음. 결과는 **구현 가능 / 추가 질문 필요 / 부분 구현 가능**으로 적는다. 선택한 첫 흐름·관련 R, 목표/입력/결과/시작과 끝, 성공·실패 수락 기준의 근거, 중요한 미확인의 영향과 다음 행동을 몇 문장으로 연결한다. 기존 기록을 참조하며 별도 승인 절차를 만들지 않는다.

전체 목적과 주요 흐름의 큰 그림을 설명할 수 있고 첫 흐름의 동작을 바꾸는 규칙이 확인되면 구현한다. 모든 상세 요구나 요약 빈칸의 완성을 기다리지 않는다. 핵심 규칙이 모호하면 그 부분만 묻고, 독립적으로 가능한 범위는 진행한다. 질문을 생략하면 공식 자료 등 충분한 근거를 적는다. 업무 결과를 바꾸는 가정을 임의 채택하지 않으며 되돌리기 쉬운 기술 선택은 D에 기록해 진행할 수 있다.

## 고객 대화 참조

아직 대화하지 않음. 실제 답변을 받은 뒤 Q번호·짧은 요약·`.hackathon/private/INTERVIEWS.md`의 해당 위치를 연결한다. 고객 원문은 여기 복사하지 않고 작업 공간 안의 Git 제외 영역에만 보관한다. 외부로 전송하지 않는다.
