# 결정 기록

아직 과제별 결정 없음. 중요한 선택이 생길 때 D번호·관련 요구사항·당시 대안·선택 이유·한계·관련 파일을 짧게 기록한다. 뒤늦게 추정한 이유는 당시 기록과 구분한다.

어떤 불편이나 문제를 해결하려 했고 왜 이 방법을 골랐는지 비개발자가 이해할 말로 먼저 쓴다. 함수·파일·ADR은 뒤에 근거로 붙인다. 고객이 정한 기준과 개발 중 우리가 정한 방식을 구분한다.

중요한 로직 선택은 구현·배정 전에 관련 R과 연결해 처리 순서·핵심 방법을 정하고, **이 방법으로 얻는 점과 감수하는 점**을 당시 이유·실제로 고려한 대안과 함께 같은 D에 짧게 남긴다. 요구사항의 로직 전략에서는 이 D를 참조한다. 이후 실제 관찰로 선택을 바꾸면 변경 이유·영향받는 검증을 이어 적고 처음부터 그 이유였던 것처럼 고쳐 쓰지 않는다. 모든 작은 수정에 새 D나 ADR을 요구하지 않는다.

고객이 개발자에게 맡긴 선택은 **실제 Q 참조 → 맡긴 범위와 지켜야 할 R/제약 → 실제 선택과 결정 주체 → 당시 이유·고려한 대안·한계 → 실제 파일·검증**을 같은 D에 짧게 남긴다. 위임은 선택할 권한의 근거이며 선택한 정책을 고객이 요청·승인했다는 뜻은 아니다. 그 범위 안에서는 재승인을 기다리지 않고 구현한다. 위임 범위가 불명확하거나 기존 필수조건과 충돌하면 필요한 업무 결과·제약을 확인한다. 별도 위임 장부나 진행 상태를 추가하지 않는다.

미정 조건 때문에 행동을 막기로 했다면 같은 D에 **실제 의존하는 R/행동·고객의 최종 결과에 미치는 영향·권한/위험 근거·더 좁게 보류할 대안·현재 제한**을 몇 문장으로 남긴다. 고객이 요구한 금지와 개발자가 보수적으로 선택한 차단을 구분한다. 검토안 제공 같은 대안도 허용 근거가 필요하며, 미정 정책을 임의 확정하거나 필요한 승인을 생략해 완료시키지 않는다. 결정 기록은 막힌 기능의 구현·검증을 대신하지 않는다.

중요한 D에만 **AI 제안 → 실제 결정 주체와 채택/수정/기각 → 당시 밝힌 이유 → 결과·검증 V/check**를 짧게 연결한다. 결정 주체는 실제로 선택한 참가자·고객·AI이며 단순히 답변을 전달하거나 AI가 자율 처리한 일을 참가자 선택으로 기록하지 않는다. 참가자가 AI를 고친 실제 사건이 있으면 ‘무엇을 보고 → 어떤 수정을 요청 → 무엇을 유지/변경/제외 → 재확인’도 같은 D에 담는다.

사건이 없으면 만들지 않고, 당시 이유를 듣지 못했으면 미기록으로 남긴다. 기존 R/Q/ADR/V를 참조하며 중요한 결정당 몇 문장으로 충분하다. 모든 기술 선택을 다시 승인받거나 별도 판단 장부를 추가하지 않는다. 민감한 원문은 Git 제외 영역에만 보관한다.

알고리즘의 품질·속도를 선택 근거로 삼았다면 같은 입력·필수 조건·목적·측정 범위에서 비교한 실제 V/check를 참조한다. 예상 복잡도·미측정과 실측을 구분하고, 비교하지 않은 후보나 숫자를 사후에 만들지 않는다.
