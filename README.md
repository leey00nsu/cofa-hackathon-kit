# Cofa Hackathon Kit

제공된 Codex로 고객 요구를 발견하고 구현·자동 검증한 뒤, **제출 전에 실제 구현의 예상 문답을 복습**하는 키트입니다. 문제별 제품 코드나 완성 답안은 포함하지 않습니다.

## 당일 시작

공식 README와 제공 파일을 확인한 뒤 **과제 작업 공간의 최상위 디렉터리**에서 실행합니다. 키트는 하위 폴더에 두어 공식 파일을 보존합니다.

```sh
git clone https://github.com/leey00nsu/cofa-hackathon-kit.git .hackathon-kit
python3 .hackathon-kit/scripts/kit.py install --workspace .
codex
```

제공된 Codex의 **대화 입력창**에 다음을 입력합니다. `$스킬명`은 셸 명령이 아닙니다.

```text
$grill-with-docs .hackathon/START_PROMPT.md를 읽고 시작 지시에 따라 진행해.
```

이미 실행 중인 Codex에는 설치된 AGENTS를 다시 읽게 하거나 새 세션을 시작합니다. 스킬 호출이 지원되지 않으면 동봉한 SKILL.md를 읽어 진행하며 Codex를 업데이트하지 않습니다. 설치에는 Python 3.10+가 필요합니다. 제공 환경에 없다면 `.hackathon-kit/templates/AGENTS.md`와 시작 안내를 Codex에게 읽게 하고 기존 환경 안에서 필요한 파일을 배치합니다. 설치기는 네트워크 요청·패키지 설치·전역 설정 변경을 하지 않습니다.

## 상황별 입력

평소에는 자연어로 대화합니다. `grill-with-docs`와 `implement`는 원본 설정상 명시 호출하며, 보조 스킬은 필요한 경우에만 사용합니다.

**참가자는 메인과만 대화합니다.** 메인은 확인된 일을 독립적으로 구현·검사할 크기로 나눠 서브에 배정하고, 자신도 핵심 작업을 계속합니다. 서브의 새 질문은 메인이 기존 답변·개발자 판단 범위를 먼저 확인한 뒤 참가자에게 취합해 전달합니다. 실제 고객 답변이 돌아오면 관련 요구·작업 지시·테스트를 갱신해 담당자에게 전달하고, 결과를 검토·통합합니다. 기본 지원 수단은 내장 서브에이전트이며, 없으면 허용된 제공 CLI 실행을 메인이 관리하고 둘 다 불가능하면 직접 진행합니다. 배정마다 참가자 승인을 반복하지 않습니다.

| 상황 | Codex 대화 입력 예시 |
| --- | --- |
| 고객 답변 전달 | Q01에 담당자가 이렇게 답했어: `[실제 답변 원문]`. 사실·가설·탐색 표와 R번호를 갱신하고 다음 질문과 지금 구현 가능한 범위를 알려줘. |
| 개발자에게 맡긴다는 답변 | Q02의 질문은 `[실제 질문]`, 답변은 `[실제 답변 원문]`이야. 맡긴 범위와 제약을 구분하고, 그 안의 선택·이유를 D에 남겨 구현해줘. 답을 못 받은 업무 사항은 따로 알려줘. |
| 구현 시작 | `$implement` 첫 흐름을 바꿀 미확인을 점검하고 확인된 범위를 구현해줘. 실제 제품 테스트 작성·실행·실패 수정까지 진행해줘. |
| 문제·첫 흐름 정리 | 기존 요구사항 정본에 문제·사용자·전체 흐름을 짧게 요약하고 첫 구현의 R과 준비 판단을 알려줘. 이미 명확한 조건은 다시 묻지 마. |
| 첫 흐름 완성 | 구현한 업무 흐름을 짧게 설명하고 담당자에게 빠진 단계를 확인할 질문을 만들어줘. |
| 서브 질문의 고객 답변 전달 | 메인이 전달한 Q03의 실제 답변은 `[원문]`이야. 관련 R·수락 조건을 갱신하고 영향받는 담당자에게 변경과 재검증 범위를 전달해줘. 다른 작업은 계속 진행해. |
| 오류 전달 | `[실제 입력·행동]`에서 기대는 `[수락 기준]`, 관찰 결과는 `[실제 결과]`야. 원인을 수정하고 같은 절차로 재검증해줘. |
| 마무리 | `$implementation-brief` 남은 작업 시간은 약 35분이야. 최종 검증과 UI 확인 목록, 구현 기반 문답과 복습본을 준비해줘. |
| 제출 전 복습 | 아직 제출을 확정하지 않았어. LAST_REVIEW.md의 핵심 질문을 하나씩 물어보고 내 설명을 실제 코드와 대조해줘. |
| 답을 보지 않고 리허설 | Q&A 리허설 시작 |
| 리허설 재개 | 아까 질문한 5문항을 이어서 할게. 기존 회차와 남은 번호를 복구하고 아직 답하지 않은 문항의 답은 보여주지 마. |
| 작업 재개 | 기존 인계 메모와 현재 파일·검증 기록을 대조하고 이어서 진행해. |

**중간 테스트는 Codex가 자동으로 수행하고 최종 UI 확인은 참가자가 합니다.** 고객 질문 중계와 중요한 범위 결정은 계속 필요합니다. 화면 결함을 수정하면 관련 자동 검사와 영향받은 UI를 다시 확인합니다.

공식 질문 제한이 없다면 키트도 총 질문·라운드 상한을 두지 않습니다. 한 번에 1~3개는 전달 묶음이며 새로운 업무 규칙·예외·흐름 확인은 계속할 수 있습니다. 고객이 개발자에게 맡긴 부분은 실제 질문·답변으로 범위를 확인하고, 기존 조건 안에서 Codex가 선택·이유·한계를 D에 기록해 재승인 없이 진행합니다. 답을 못 받은 업무 사항과 구분하며 자체 선택을 고객 요청으로 바꾸지 않습니다. 고객에게는 업무 흐름과 예시 결과가 맞는지 확인하고 실제 코드 동작은 테스트·최종 UI로 확인합니다.

진행 순서는 **문제·전체 흐름 요약 → 첫 흐름의 R·근거·수락 조건 → 구현 준비 판단 → 실패하는 검사 → 최소 구현·자동 검증 → 고객 피드백과 같은 기록 갱신**입니다. 공식 자료가 충분히 명확하면 질문을 반복하지 않고, 핵심 업무 규칙이 모호하면 그 부분만 확인하며 독립 작업은 계속합니다.

PRD(무엇을 왜 만드는지 설명하는 문서)의 핵심은 기존 요구사항 정본 상단 요약에 둡니다. 상세 업무 규칙·수락 조건·구현/검증 상태는 R 행을 참조하며 새 PRD 파일·버전 사본·추가 승인 단계를 만들지 않습니다. 근거의 확실성, 이번 범위, 구현·검증 진행은 구분합니다. MVP는 먼저 완성할 작은 흐름이며 공식 최종 필수 요구를 없애는 기준이 아닙니다. 의미가 바뀌면 요약과 관련 R을 함께 고치고 영향받는 검증을 다시 확인합니다.

## 작업 중 참고

- [시작 지시](docs/START_PROMPT.md): 공식 자료·문제 요약·첫 흐름 준비 판단부터 시작.
- [인터뷰 절차](docs/INTERVIEW_PROTOCOL.md): 여섯 영역 탐색, 구현 진입, 구현 중 고객 확인.
- [자동 검증](docs/AUTOMATED_TESTING.md): Matt TDD, 실제 함수/API/저장/업무 흐름 검사, 최종 UI 목록. 상세 CLI는 여기서 필요할 때 참조.
- [메인의 병렬 운영](docs/references/orchestration.md): 작업 배정, 서브 질문 → 고객 답변 → 관련 작업 재개, CLI 대안, 결과 검토·통합. 나누거나 배정받을 때 참조.
- [Q&A Defense](docs/DEFENSE.md): 작은 흐름 구현·자동 검증 뒤 처리 흐름·실제 함수·업무 규칙·자체 선택·검증·한계를 짧게 연결. 기존 R/D/V와 ADR을 참조하며 새 장부를 만들지 않습니다.

운영·Matt 적용·Evidence 규칙은 설치되는 AGENTS에 모았습니다. 기존 요구사항 정본과 R번호를 유지하고 고객 Q → 요구·수락 조건 → 결정/실제 파일 → 실행 결과를 연결합니다. 원문·로그·복습본은 로컬 Git 제외 영역에 둡니다.

생성 문서는 **비개발자가 읽을 수 있는 쉬운 한국어**로 씁니다. 사용자가 하는 일·프로그램의 처리·결과와 선택 이유를 먼저 설명하고, 함수명·파일·명령은 뒤에 확인 근거로 붙입니다. 전문용어는 필요한 경우 뜻을 풀어 쓰며 실패하거나 아직 확인하지 못한 조건도 함께 적습니다.

자료가 있는 과제에서는 한 줄의 뜻·식별자·단위·기간·계산 대상을 고객 답변과 연결하고 해당 위험만 자동 검사합니다. 중요한 결정에는 AI 제안과 참가자가 실제로 고른 것·이유·결과를 구분해 남깁니다. 일반 기술 선택마다 재승인을 요구하지 않습니다.

검사기는 pytest의 앞선 실패가 뒤의 성공에 가려지지 않게 처리하고, 새 실행의 전체 로그가 남아 있으며 내용이 같은지도 대조합니다. 여러 pytest 실행의 성공 요약이 섞이면 집계 범위 미확인으로 남깁니다. 내용 지문이 없는 이전 기록은 보존하며 추가 로그 검사는 미확인으로 표시합니다.

답변 제목만으로 ‘답변 대기’를 확인 사실로 읽지 않고, 끊긴 표의 요구사항도 조용히 생략하지 않습니다. 예상 실패만 있는 테스트는 실제 실행과 일반 성공을 구분합니다. 문답은 참조한 과거 실행이 현재 코드·기준에도 맞는지 표시하며, 오래되거나 비교하지 못한 근거가 있으면 문서가 일치해도 검증 완료로 반환하지 않습니다.

## 마무리 시간 확보

최신 공식 안내와 실제 타이머에 맞춰 남은 일을 배치합니다. 타이머는 자동으로 읽지 않으므로 참가자가 남은 시간을 알려줍니다. 늦어지면 기능 범위를 줄이고, 세션이 바뀌어도 초기 인터뷰부터 다시 시작하지 않습니다.

| 시점 | 확인할 지점 |
| --- | --- |
| 첫 구현 전 | 첫 흐름을 바꿀 업무·성공 기준·중요한 미확인 탐색 |
| 첫 흐름 뒤 | 고객에게 실제 업무 흐름·빠진 단계 확인 |
| 남은 확인·제출을 마칠 여유가 있을 때 | 범위 확정, 유효한 자동 검사 재사용과 필요한 수정·회귀, 최종 UI 확인 |
| 제출 확정 전 | 구현 문답·근거 검사, 참가자 복습·자기 설명 |
| 확정·후속 절차에 필요한 여유를 남기고 | 필수 파일·저장·미리보기 확인 후 참가자가 직접 확정 |

연장 공지와 타이머가 다르면 정식 채널로 확인하고, 적용이 확인되기 전에는 더 이른 종료에 맞춰 저장·제출 여유를 둡니다. 장애 문의에는 **시각 / 발생 단계 / 한 행동 / 기대·실제 오류 / 이미 한 복구와 결과 / 남은 시간** 중 필요한 관측만 적습니다. 앱 오류·플랫폼/감독 연결·입력 대기를 구분하고 비밀정보는 제외합니다. 문의는 참가자가 허용된 채널로 직접 전달하며, AI 중단 이후 도움을 다시 요청하는 절차로 만들지 않습니다.

제출 확정 **전에** 아래 순서를 확인합니다. 해당 회차에 실제로 있는 단계만 사용하며, 저장이나 제출 확정만으로 전체 완료라고 말하지 않습니다.

1. 필수 파일과 최신 내용이 저장됐는지 확인합니다.
2. 참가자가 제출을 확정하고 실제 확정 표시를 확인합니다.
3. 공식 안내에 후속 절차가 있으면 참가자가 규칙에 따라 직접 마칩니다.
4. 실제 최종 완료 화면·접수 표시 등 안내된 확인까지 마칩니다. 표시가 없으면 확인한 단계와 오류를 정식 채널에 전달합니다.

AI는 확정 전까지 이 안내를 준비하고, 제출 확정 이후 AI 중단과 실제 Q&A의 AI 금지 규칙을 따릅니다. 후속 화면·문항·접수증이 반드시 있다고 가정하거나 자동으로 제출하지 않습니다.

`$implementation-brief`는 `.hackathon/study/IMPLEMENTATION_QA.md`와 `LAST_REVIEW.md`를 작성하고 `verify-qa`로 근거·최신성을 검사합니다. 실제 서술형 문항이나 점수를 보장하지 않으며 참가자 이해는 직접 설명으로 확인합니다.

과제 작업 공간의 Codex에 **`Q&A 리허설 시작`**이라고 입력하면 현재 코드·요구·공개 가능한 고객 근거·Git 변경·테스트·DEFENSE를 분석해 예상 질문 **5개만 먼저** 제시합니다. 자료와 AI 도움 없이 1~5번에 답하면 정확성·누락·잘못된 가정을 실제 코드와 대조하고 보충 학습 위치를 알려줍니다. 필요하면 새 질문 5개로 다시 연습합니다. 별도의 스킬 명시 호출은 필요하지 않습니다.

리허설은 아키텍처·예외 처리·자체 결정·검증 근거·한계를 중심으로 합니다. 기존 6개 주제 문답은 답을 함께 읽는 복습용이고, 5문항 리허설은 답을 가리고 이해를 확인하는 연습입니다. 실제 출제는 달라질 수 있습니다. 실제 응답·피드백은 `.hackathon/study/DEFENSE_REHEARSALS.md`에 보존합니다.

질문 제시 때 같은 기록에 질문·답변 대기 번호·당시 근거를 먼저 남겨 세션 변경 후에도 답을 가린 상태로 이어갑니다. 답변 대기 중 관련 구현이 바뀌면 해당 질문은 평가를 보류하고 새 전제로 다시 묻습니다. 복습 재호출만으로 유효한 최종 테스트를 반복하지 않습니다.

답변에서 막힌 흐름은 같은 입력 한 건의 값 변화를 실제 코드와 3~5단계로 연결해 보충 설명합니다. 실제 실행 관찰과 코드 해석을 구분하고, 다른 입력으로 다시 직접 답한 뒤 이해 상태를 확인합니다. 첫 질문 전에는 정답을 보여주지 않습니다.

추가 시험의 **날짜·작업 제한·문항 수·답변 시간은 최신 공식 안내**를 따릅니다. 이전 시험의 일정을 그대로 적용하지 않습니다. 문항 준비 대기도 절대 종료 시각에 포함되는지 확인합니다. 문답 생성·복습·리허설은 허용된 사전 학습 시간에 마치며 **제출 확정 후 AI 중단 규칙과 실제 Q&A의 AI 금지 규칙을 준수**합니다. 노트·코드 열람 가능을 전제하지 않습니다. 개인 리허설은 해당 연습의 시간 조건을 따릅니다.

## 설치와 유지

기본 설치는 Matt core 10개 + 자체 문답 스킬 1개입니다. `--matt all`은 Matt 27개 + 자체 1개, `--matt none`은 자체 스킬만 배치합니다. Matt 전체 원본은 고정 커밋으로 보존하며 upstream setup은 필요 없습니다.

기존 README·AGENTS·장부·`docs/DEFENSE.md`를 보존합니다. 요구사항 정본은 설치 결과와 `.hackathon/install.json`의 `requirements_path`를 따르며 여러 후보가 있으면 `install --requirements <기존경로>`로 지정합니다. 충돌·이미 추적된 비공개 경로는 쓰기 전에 중단합니다. 진행 중인 작업에 재설치를 강제하지 말고 필요한 지침만 선별 반영합니다.

세션이 바뀌면 기존 Matt 인계 메모에 코드/검증 상태·남은 질문·서버·다음 행동을 짧게 남기고 재개 때 현재 상태와 대조합니다. 메인은 작업별 실제 세션/프로세스·담당 파일·질문 대기·지시/결과 위치도 함께 대조하고, 결과를 모르는 실행을 확인해 중복 작업을 피합니다. 지원·허용되는 독립 작업은 메인이 배정하며 파일별 담당과 공용 기록·통합 서버 담당을 구분합니다.

인계 파일의 정확한 경로·대상 작업 공간·역할을 함께 전달하고 최근 파일로 임의 대체하지 않습니다. 공유 의존성 설치·공용 설정 변경은 한 담당자가 조정하고 영향받는 작업에 알립니다. 별도 설치 잠금이나 추가 세션을 필수화하지 않습니다.

공개 키트의 DEFENSE는 빈 양식입니다. **설치된 과제의 `docs/DEFENSE.md`는 기본 Git 제외**이며 실제 고객 원문을 복사하지 않습니다. 이미 추적된 DEFENSE는 ignore만으로 보호되지 않아 설치를 중단합니다. 기존 파일과 이력을 검토하고 공개 여부를 따로 결정합니다. Defense 갱신은 실제 코드 테스트를 무효화하지 않지만, 기존 생성 문답은 다시 검토·렌더해야 합니다.

당일에는 제공된 Codex·허용 모델을 사용하고 업데이트·외부 AI/개인 키·Computer Use·Git Push·외부 전송을 하지 않습니다. 최신 운영 안내와 공식 과제가 우선합니다. 공개할 자료는 별도 승인받고 사용 저장소는 2차 결과 통지 전까지 Public으로 유지합니다.

키트 자체를 수정할 때의 검증과 공개 절차는 [관리 지침](AGENTS.md)을 따릅니다. 라이선스는 MIT이며 [Matt 원본 저작권·고정 커밋·출처](THIRD_PARTY.md)를 보존합니다.
