# 시작 지시

아래를 제공된 Codex의 대화 입력창에서 사용한다. 짧게 시작하려면 `$grill-with-docs .hackathon/START_PROMPT.md를 읽고 시작 지시에 따라 진행해`라고 입력한다. 이후의 상황별 문장은 [입력 예시](INPUT_EXAMPLES.md)를 참고한다.

```text
$grill-with-docs

현재 작업 공간의 공식 README·과제 안내와 AGENTS.md를 먼저 읽고, .hackathon/OPERATING_RULES.md, .hackathon/INTERVIEW_PROTOCOL.md, .hackathon/SKILLS.md를 읽어 적용해라.
제공된 Codex·허용 모델을 그대로 사용하며 업데이트하지 마라. 외부 AI·개인 키·Computer Use·Git Push·외부 전송은 사용하지 마라.

공식 과제의 필수 파일·제출 위치·실행 방법을 우선 파악하라. 제공 파일과 README를 보존하라.
나는 오른쪽 실무자 에이전트와 직접 대화하고, 너에게 답변을 전달한다.
업무 사실을 나에게 결정하라고 묻지 말고, 실무자에게 전달할 열린 질문을 1~3개씩 제안하라.
확인된 사실·가설·남은 질문을 구분해 .hackathon/REQUIREMENTS.md에 근거와 수락 기준을 기록하라.
EVIDENCE_TRACKING.md를 적용하라. 질문·실제 답변 원문은 .hackathon/private/INTERVIEWS.md에 Q번호로 보관하고 요구사항에는 R번호·Q참조·요약만 남겨라. 원문·로그·복습본의 Git 제외를 확인하고 이미 추적된 파일은 별도로 점검하라.
업무 흐름, 입력과 결과, 판단 기준, 사람의 판단과 권한, 예외와 기록 보존, 우선순위와 성공의 여섯 영역을 요구사항 장부에서 점검하라.
첫 사례나 수락 기준 하나만으로 인터뷰를 끝내지 마라. 선택한 흐름을 바꾸는 중요한 미확인은 질문 후 확정하되, 독립적으로 진행 가능한 작은 부분은 구현할 수 있다.
기능 필요 여부와 우선순위를 구분하라. ‘있으면 편하다’를 고객이 정한 P0로 기록하지 마라.

매 답변을 받은 뒤 [확인된 사실·근거] [미확인·구현 영향] [다음 고객 질문 1~3개] [지금 구현 가능한 범위]로 응답하라.
추가 질문이 없다면 현재 범위를 구현할 수 있는 근거와 남은 미확인의 영향을 설명하라.
첫 작동 흐름 완성 후와 제출 전 범위 확정 때 고객 확인 질문을 제안하라. 이미 답변으로 확인됐다면 그 근거를 남기고 반복은 생략하라.

Matt 스킬은 필요한 것만 선택하라. 인터뷰의 질문 수와 설계 확정을 무제한 늘리지 마라.
기술 선택의 이유·기각한 대안은 .hackathon/DECISIONS.md, 실제 검증과 한계는 .hackathon/VERIFICATION.md에 짧게 기록하라.
기존 R번호로 결정·구현 파일·실제 테스트와 결과를 연결하라. 전체 수락 조건의 실행 근거가 있어야 Verified이며 미실행·화면 확인 대기는 통과가 아니다. 필요한 스킬만 사용하고 기존 장부를 중복 작성하지 마라.
요구사항 정본은 설치 결과/manifest의 requirements_path를 따르라. 검증 명령은 VALIDATION_TOOLS.md를 참고해 관련 R번호·실행 지문·실제 결과를 연결하라. 테스트 0건/전부 skip을 성공으로 설명하지 마라. 첫 작동 흐름 뒤에는 내 직접 설명도 제안하되 미응답이면 대기로 남기고 독립 작업을 이어가라.
Browser 조작은 내가 직접 한다. CLI 검증은 실행한 명령·결과만 기록하라.

완료에는 실제 구현·검증뿐 아니라, $implementation-brief로 만든 구현 기반 예상 문답과 마지막 복습본도 포함된다.
약 145~155분부터 기능 확장을 줄이고 문답 생성·검토·복습 시간을 확보하라. 제출 확정은 내가 직접 한다.
현재는 공식 과제를 읽은 뒤 첫 실무자 질문과 그 질문이 구현에 미치는 영향부터 알려줘.
```
