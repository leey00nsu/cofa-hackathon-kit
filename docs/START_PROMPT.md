# 시작 지시

제공된 Codex 대화 입력창에서 `$grill-with-docs .hackathon/START_PROMPT.md를 읽고 시작 지시에 따라 진행해`라고 입력한다.

공식 README·과제 안내와 설치된 AGENTS.md를 읽고, [인터뷰 절차](INTERVIEW_PROTOCOL.md)를 적용한다. 제공 파일·필수 제출 경로·실행 방법을 확인한다.

기존 앱·지정 스택이 없는 새 웹 과제는 Next.js App Router·TypeScript·Tailwind·shadcn/ui와 PostgreSQL을 기본으로 한다. 실제 DB·Docker 필수 여부와 제공 환경을 먼저 확인한다. 스타터가 필요할 때만 [스택과 실행 안내](references/stack.md)를 읽고 배치한다. 기존 코드·지정 DB·컨테이너 조건은 보존하며 시작할 때 전체 설정을 다시 만들지 않는다.

별도 작업자·검토자로 배정된 세션이 아니면 참가자의 대화 창구인 메인으로 진행한다. 독립 작업이 있으면 [병렬 작업 절차](references/orchestration.md)를 필요한 시점에 읽고, 지원·허용되는 수단으로 스스로 배정·질문 취합·답변 전달·결과 검토·통합한다. 참가자에게 각 작업자의 지시·진행 관리를 맡기지 않는다. 작업자로 배정됐다면 받은 범위와 관련 근거부터 읽고 메인에게 질문·결과를 반환하며 초기 인터뷰를 다시 시작하지 않는다.

실제 과제 지시서 경로와 참고 키트 폴더를 먼저 구분한다. 기존 작업이 있거나 ‘이어서 진행’ 요청이면 재초기화하지 말고 AGENTS의 재개 규칙과 기존 인계 메모·장부·파일을 대조해 다음 행동부터 이어간다. 기록만 보고 테스트 완료나 서버 상태를 추정하지 않는다.

인계는 정확한 파일 경로·대상 작업 공간·역할을 확인한다. 위치가 없다고 최근 메모를 임의로 대신 읽지 않는다. 답변을 기다리는 5문항 리허설이 있으면 기존 `.hackathon/study/DEFENSE_REHEARSALS.md`에서 질문과 대기 상태를 복구하며, 참가자가 복습 전환을 명시하지 않았다면 정답 포함 문서를 먼저 안내하지 않는다.

참가자는 고객에게 질문을 전달하고 실제 답변을 중계한다. 기존 요구사항 정본은 설치 결과 또는 `.hackathon/install.json`의 `requirements_path`를 따른다.

먼저 공식 자료와 받은 답변으로 기존 요구사항 정본의 ‘문제와 첫 흐름 요약’과 관련 R을 정리한다. 다른 이름의 기존 절이 같은 역할이면 재사용한다. 문제·사용자·주요 흐름·최종 필수와 첫 구현 범위를 아는 만큼 설명하고, **누가 어떤 최종 결과를 받아 업무를 마치는지**를 연결해 첫 흐름의 구현 준비를 판단한다. 초안·저장 성공과 최종 결과를 구분한다. 별도 PRD·새 상태 목록·추가 승인 절차는 만들지 않는다.

첫 흐름을 바꿀 중요한 미확인이 있으면 담당자에게 전달할 열린 질문 1~3개와 각 답변의 영향을 제안한다. 공식 자료에 이미 명확하면 근거와 ‘구현 가능’ 판단을 알리고 불필요한 인터뷰 없이 진행한다. 일부만 명확하면 관련 부분만 보류하고 독립 작업을 이어간다. 답변마다 사실·가설·남은 질문·가능 범위를 갱신한다. 구현 전 [자동 검증](AUTOMATED_TESTING.md)을 읽고 관련 R·수락 조건 → 실패하는 동작 검사 → 최소 구현 → 실제 검증 순서를 따른다.

구현·배정 전에는 기존 요구사항의 ‘구현 진입 판단’에 관련 R과 입력/결과, 처리·분기 순서, 핵심 구현 방법, 오류 처리, 선택 이유·대안 D와 검사 방법을 몇 줄로 설명한다. 첫 흐름 완성과 중요한 규칙 변경 뒤에는 기존 코드 리뷰에서 빠진 반례를 살핀다. 첫 자동 검증된 핵심 흐름과 중요한 결정 변화는 메인이 쉬운 설명과 짧은 본인 설명 질문을 먼저 제안한다. 최종 UI 대기는 별도로 표시하며 이 설명을 마지막까지 미루지 않는다. 세 절차는 같은 기록을 재사용하고 추가 승인이나 전체 개발 중단을 만들지 않는다. 답을 가린 리허설이 진행 중이면 미응답 문제의 답을 먼저 설명하지 않는다.

고객이 정한 결과·제약, 개발자에게 명확히 맡긴 범위, 아직 답을 못 받은 업무 사항을 구분한다. ‘개발자가 정할 부분’이면 인터뷰 절차에 따라 실제 Q와 범위·제약을 연결하고, 그 안의 선택·이유·한계를 기존 D에 남겨 재승인 없이 구현한다. 범위가 불명확하면 필요한 결과만 확인한다. 위임을 다른 업무 규칙으로 확대하거나 자체 선택을 고객 요청으로 기록하지 않는다. 1~3개는 한 번에 전달할 질문 수이며 전체 라운드 제한이 아니다. 고객의 흐름 확인과 실제 실행 검증은 따로 기록한다.
