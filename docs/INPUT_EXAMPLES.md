# 상황별 Codex 입력 예시

아래 문장은 **웹 IDE 터미널에서 실행 중인 Codex의 대화 입력창**에 넣는다. 평소에는 자연어로 대화하고, 인터뷰·구현·마무리로 넘어갈 때 스킬 이름을 한 번 붙인다. `$스킬명`은 일반 셸에 실행할 명령이 아니다.

Matt 원본의 `grill-with-docs`와 `implement`는 자동 선택이 꺼져 있어 명시적으로 호출한다. 나머지 보조 스킬은 상황에 맞춰 Codex가 활용하도록 한다. 실제 제공 버전에서 스킬이 보이지 않으면 `/skills`와 설치 상태를 확인하고, 업데이트나 제한 우회 대신 해당 SKILL.md를 읽는 방식으로 진행한다.

## 빠르게 찾기

| 상황 | Codex에 입력할 예시 |
| --- | --- |
| 인터뷰 시작 | `$grill-with-docs` `.hackathon/START_PROMPT.md`를 읽고 담당자에게 전달할 첫 질문을 만들어줘. |
| 고객 답변 전달 | 담당자가 이렇게 답했어. `[답변 원문]` 탐색 표를 갱신하고 미확인·구현 영향·다음 질문을 정리해줘. |
| 구현으로 전환 | `$implement` 첫 흐름에 영향을 주는 중요한 미확인을 점검한 뒤, 확인된 범위를 구현해줘. |
| 첫 흐름 완성 후 | 지금 구현한 업무 흐름을 담당자에게 설명하고 빠진 단계를 확인할 질문을 만들어줘. |
| 수정·추가 요청 | 이 화면에서 중복 입력하면 오류가 나. 원인을 확인하고 수정·검증해줘. |
| 제출 전 마무리 | `$implementation-brief` 남은 작업 시간은 35분이야. 검증을 마치고 예상 문답과 복습본을 만들어줘. |

수정 예시는 관찰 결과의 작성 방식이다. 실제로 보지 않은 오류나 고객 답변을 그대로 전달하지 않는다.

## 1. 설치 후 인터뷰 시작

```text
$grill-with-docs

.hackathon/START_PROMPT.md를 읽고 시작 지시에 따라 진행해.
공식 과제와 기존 파일을 확인한 뒤, 담당자에게 전달할 첫 질문 1~3개와 각 질문이 구현에 미치는 영향을 알려줘.
```

Codex가 제안한 질문을 참가자가 오른쪽 실무자 채팅으로 전달한다. 담당자 답변을 받은 뒤 아래 형식으로 돌아온다.

## 2. 고객 답변 전달과 다음 판단

```text
질문 Q01에 담당자가 이렇게 답했어.

[여기에 실제 답변 원문]

확인된 사실·가설·남은 질문을 구분해서 요구사항 장부에 반영해줘.
여섯 영역의 탐색 표도 갱신해줘.
[확인된 사실·근거] [미확인·구현 영향] [다음 고객 질문 1~3개] [지금 구현 가능한 범위]로 알려줘.
추가 질문이 없다면 구현해도 되는 근거를 설명해줘. 기능 필요 여부와 고객이 정한 우선순위를 구분해줘.
```

구현 중 새 답변이 와도 같은 방식으로 전달한다. 업무 사실은 담당자 답변으로 확인하고, 기술적 선택은 Codex의 제안과 참가자의 판단으로 정한다.

## 3. 첫 구현 시작

```text
$implement

첫 흐름을 바꾸는 중요한 미확인이 남았는지 INTERVIEW_PROTOCOL.md 기준으로 먼저 점검해줘.
남아 있다면 담당자에게 전달할 질문을 만들고, 독립적으로 구현 가능한 부분을 구분해줘.
확인된 범위로 입력부터 결과 확인까지 첫 작동 흐름을 구현해줘.
공식 필수조건과 .hackathon/REQUIREMENTS.md를 기준으로 하고, 미확인 업무 규칙은 임의로 확정하지 마.
핵심 규칙을 실제로 검증하고, 중요한 선택과 검증 결과를 장부에 기록해줘.
```

`tdd`, `codebase-design`, `code-review` 같은 보조 스킬은 구현 범위에 맞춰 활용한다. 단계별 스킬을 계속 다시 입력할 필요는 없다.

첫 흐름이 완성되면 다음처럼 담당자의 피드백을 받는다.

```text
지금 구현한 입력 → 판단 → 행동 → 기록 흐름을 업무 언어로 짧게 정리해줘.
실제 한 건을 이 흐름으로 처리할 때 빠지거나 다른 단계가 있는지 담당자에게 물을 질문을 만들어줘.
고객 답변을 받은 뒤 바뀐 결정과 남은 미확인을 기록하자.
```

제출 전 범위를 확정할 때도 확인된 필수조건과 성공 기준을 대조한다. 기존 답변으로 이미 확인된 사항은 근거를 남기고 반복 질문하지 않는다.

## 4. 실행 결과 전달과 수정

```text
내장 Browser에서 직접 확인한 결과야.

한 동작: [실제 입력과 클릭 순서]
기대 결과: [확인된 수락 기준]
실제 결과: [관찰한 화면 또는 오류 문구]

원인을 확인하고 수정한 뒤 같은 조건으로 다시 검증해줘.
화면을 다시 확인해야 하면 내가 수행할 절차를 알려줘.
```

이 단계는 자연어로 진행한다. Codex는 필요하면 `diagnosing-bugs`를 사용한다. Browser 조작은 참가자가 직접 하고, Computer Use나 브라우저 자동 조작은 사용하지 않는다.

## 5. 남은 시간 전달과 제출 전 마무리

```text
$implementation-brief

남은 작업 시간은 약 35분이야.
.hackathon/FINISH_PROMPT.md를 읽고 새 기능 추가를 줄여줘.
구현·검증을 마무리하고, 실제 코드와 기록에 근거한 예상 문답과 LAST_REVIEW.md를 만들어줘.
내가 복습하고 직접 제출할 시간을 남겨줘.
```

시험 타이머를 이 준비물이 자동으로 읽지는 않는다. 참가자가 상단 타이머를 보고 남은 시간을 알려준다. 약 145~155분에 마무리로 전환하되 실제 남은 시간과 작업 상태에 맞춰 조정한다.

## 6. 제출 전 복습

```text
아직 제출물을 확정하지 않았어.
LAST_REVIEW.md의 핵심 질문을 하나씩 물어봐줘.
내가 내 말로 답하면 실제 구현과 다른 부분이나 빠진 한계만 짚어줘.
```

위 연습은 **과제풀이 단계에서만** 한다. 복습과 문답 생성은 제출물 확정 전에 끝낸다. 확정 후에는 AI 사용을 중단하고 실제 후속 서술형에 직접 답한다. 실제 서술형 문항을 다시 AI에 보내거나 복사·붙여넣기하지 않는다. 서술형 중 문서 열람이 가능하다고 가정하지 않는다.
