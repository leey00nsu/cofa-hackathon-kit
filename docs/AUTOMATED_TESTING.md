# 중간 자동 검증과 최종 UI 확인

구현 단계에 읽는다. 실행 기록·장부 감사·수동 관찰·환경 조회의 명령 구문이나 판정 범위가 필요할 때만 [상세 명령 참조](references/validation-tools.md)의 해당 절을 읽는다.

기본은 **중간 검증은 Codex, 최종 실제 UI 확인은 참가자**다. Matt 원본 tdd/implement/code-review를 유지하고 아래 대회용 절차를 적용한다. 고객 업무 규칙의 질문·첫 흐름 뒤와 범위 확정 때의 고객 확인은 계속한다. 이때 설명하는 것은 업무 흐름이며 고객에게 실제 화면을 조작했다고 가정하지 않는다.

병렬 작업자는 배정된 기능의 실패 테스트부터 실제 실행·수정까지 맡고, 질문·중요한 선택·파일·실행 근거를 메인에게 반환한다. 메인이 기존 R/D/V·DEFENSE를 갱신한다. [병렬 작업 절차](references/orchestration.md)에 따라 작업별 실행 ID·임시 데이터를 구분하고, 통합 후 안정된 코드에서 실제 연결과 회귀를 확인한다. 다른 작성자의 변경 중 실행되거나 다른 작업 폴더에서 얻은 PASS를 최종 근거로 바로 승격하지 않는다. 새 고객 답변으로 기준이 바뀌면 관련 담당과 테스트에 전달하고 기존 실패·결과를 보존한다.

## 구현할 때의 반복

1. 요구사항 정본의 문제·첫 흐름 요약과 구현 진입 판단을 읽고 관련 R의 수락 조건·Q/공식 과제 근거와 명시적 위임 범위 안의 선택 D를 확인한다. 대표 입력부터 결과까지 검증할 수 있는 작은 업무 흐름을 선택한다. 구현·배정 전에 같은 절에 처리·분기 순서, 핵심 방법·연결, 오류 처리, 선택 이유·실제 대안 D, 검사 경계와 기대값 근거를 몇 줄로 정리한다. 답을 못 받은 업무 규칙은 질문으로 남기고 독립 구현을 진행한다.
2. 합의한 공개 테스트 경계에서 실패하는 동작 검사를 먼저 작성한다. 이미 합의된 테스트 경계는 재사용하며 테스트마다 참가자 승인을 반복하지 않는다. 기존 동작이 이미 통과하면 그 사실을 적고 실패 이력을 소급 생성하지 않는다.
3. 실제 제품 함수를 구현·수정하고 테스트를 실행한다. 결과를 읽고 실패 원인을 고쳐 같은 절차를 새 실행 ID로 재실행한다. 구현을 그대로 복제한 테스트용 앱이나 같은 계산식으로 만든 기대값을 검증으로 삼지 않는다.
4. 작은 수정 직후는 관련 검사, 업무 흐름 완성 때는 통합/회귀 검사, 기능 동결 뒤 최종 UI 확인 전은 전체 관련 검사를 수행한다. 이미 통과한 검사를 이유 없이 반복하지 않는다.
5. `kit.py check --requirement <R번호>`로 실제 실행을 연결하고, 자동 검증 범위·결과·남은 최종 UI 항목을 장부에 갱신한다. 요약은 의미·범위가 바뀐 부분과 관련 R 참조만 갱신하며 진행 상태를 복제하지 않는다. 실행·수정·재검증은 Codex가 맡고 다음 독립 흐름으로 이어간다.

실패를 해결하려고 고객 조건을 바꾸거나 테스트를 느슨하게 만들어서는 안 된다. 실제 수락 조건 오류·새 정보는 근거를 기록하고 갱신한다. 업무 답변·권한·환경 제한 때문에 막히면 필요한 질문/제한을 알리고, 하지 못한 검증을 미검증으로 남긴다. 브라우저/Computer Use를 사용하지 않고 제공 환경의 제한도 변경하지 않는다.

고객이 맡긴 범위에서 정한 정책은 D를 참조하는 수락 조건으로 실제 검사한다. 검사 통과는 그 선택대로 동작했다는 근거이며 고객이 그 정책을 요청했다는 근거가 아니다. 고객의 흐름 설명 동의·예시 결과 확인도 실제 코드 실행이나 UI 관찰을 대신하지 않는다.

## 첫 흐름 뒤 빠진 반례 검토

첫 작동 흐름과 중요한 업무 규칙·로직 변경 뒤에는 기존 `code-review`의 요구사항 대조에 **현재 검사가 놓친 반례 찾기**를 명시한다. 지원·허용되며 도움이 되면 읽기 전용 검토자에게 맡기고, 없으면 메인이 직접 검토했다고 표시한다. 모든 작은 수정마다 별도 전체 리뷰를 더하지 않는다.

실제 R/Q/D·제품 코드·현재 테스트를 대조한다. 과제에 해당하는 빈 입력·경계 바로 안팎·제외 대상과 오류의 조합·중복·상태/처리 순서·중단/입력 교체 중 위험한 사례를 고른다. 한 테스트의 정상 통과만으로 다른 조합도 안전하다고 가정하지 않는다. 없는 기능이나 업무 정책을 검사 때문에 추가하지 않는다.

검토자는 **구체적인 입력/행동 → 기대 결과와 근거 또는 미확인 → 기존 검사에서 빠진 부분 → 실제 관찰/미실행**을 메인에게 짧게 반환한다. 메인은 기존 V의 해당 흐름에 필요한 후보와 처리 결과만 남긴다. 제안한 사례는 성공 기록이 아니다. 업무 기준이 불명확하면 고객 질문으로, 확인된 기준과 구현이 다르면 현재 작성 담당에게 실패 테스트·수정·같은 절차 재실행으로 연결한다. 실제 실패·새 질문·남은 위험은 기존 R/V에 보존하고 관련 전략·D·DEFENSE도 갱신한다.

## 자동 검증의 층

| 대상 | 검사 | 확인하지 못하는 범위 |
| --- | --- | --- |
| 업무 규칙 | 확인된 입력·결과·제외·경계·오류를 실제 공개 함수로 검사 | 아직 발견하지 못한 고객 규칙 |
| API | 실제 앱 요청의 상태 코드·내용·잘못된 요청·업무 상태 | 화면 이벤트와 레이아웃 |
| 기록 보존 | 임시 저장소에서 저장→재조회→같은 저장소로 서버 재시작→재조회 | 실제 운영 데이터/환경 전부 |
| 업무 흐름 | 실제 앱의 여러 API를 순서대로 실행해 결과/중복/실패를 확인 | 브라우저에서 버튼이 실제로 연결됐는지 |
| 프런트엔드 로직 | 제품이 사용하는 입력 검증·필터·정렬·표시 데이터 함수, 제공 도구의 빌드/구문 검사 | 실제 렌더링·클릭·사용성 |
| 최종 UI | 참가자가 제공 Browser에서 실제 조작·입력·결과·새로고침·표시 확인 | 자동 통과로 대체하지 않음 |

정상 입력·제외/경계·확인된 실패 조건은 실제 요구에 맞춰 선택한다. 없는 권한·상태·외부 연동을 테스트를 위해 새로 만들지 않는다. `/health` 성공이나 HTML 응답 한 번을 업무 흐름 전체 통과로 확대하지 않는다. 프로그램에서 직접 호출한 UI 처리 함수가 통과해도 실제 화면 이벤트 연결은 최종 UI 확인에 남긴다.

## 자료·계산 과제에서 선택할 검사

[인터뷰 절차](INTERVIEW_PROTOCOL.md#자료가-있는-과제에서-먼저-확인할-뜻)에서 확인한 한 줄의 뜻·식별자·단위·기간·반복/누락 처리 기준을 관련 R과 연결한다. 아래는 **검사 선택용 가상 사례**이며 고객 규칙이나 실행 결과가 아니다. 해당하는 위험만 실제 제품 테스트에 맞춘다.

- **비율의 대상:** 100개 중 99개, 2개 중 1개인 경우 전체 물품 비율은 100/102, 그룹 비율의 단순 평균은 74.5%다. 고객이 원하는 대상을 먼저 정하고 맞는 기대값을 손으로 확인한다. 분모 0·빈 값의 표현도 업무 기준을 따르며 임의로 0%로 바꾸지 않는다.
- **결합·반복:** 같은 키가 양쪽에 2행과 3행이면 6행으로 늘 수 있다. 결합 전후 행·고유 식별자·미연결 수·관련 합계를 대조하고, 늘어난 것이 의도한 관계인지 확인한다. 필터링이면 입력=결과+제외를 확인할 수 있지만 집계·일대다 결합에 같은 등식을 강제하지 않는다. `001`/`1`, 복합 식별자, 재검사도 확인된 기준으로 검사한다.
- **시간과 계산:** 시작·종료 경계, 단위·반올림·취소/제외 항목을 실제 기준으로 검사한다. 구현과 독립적인 작은 손계산 또는 단순 기준 방법을 사용한다. 배정·최적화라면 작은 입력에서 제약을 따로 확인하고, 해가 나왔다는 것과 최적이라는 것을 구분한다.
- **배정·최적화일 때만:** 목적의 방향·단위·필수 조건을 R/Q와 연결하고 근거 없는 비용·벌점·동점 규칙을 넣지 않는다. 결과에 전체 필수 대상이 빠짐없이 있는지, 중복·제약 위반·목적값을 독립 확인한다. ‘유효한 안 발견·최적성 미증명’, ‘최적성 근거 있음’, ‘불가능 증명’, ‘제한 내 못 찾음’, ‘실행 실패’를 실제 지원 범위에서 구분하고 종료 이유를 남긴다. 시간 안에 못 찾은 것을 불가능으로, 작은 입력의 정답 일치를 전체 최적성 증명으로 설명하지 않는다. 솔버가 제공하는 보장·오차·하한/상한도 실제 설정과 의미를 확인한 경우만 기록한다.
- **성능·품질 개선을 주장할 때만:** 같은 입력·필수 조건·목적·측정 범위·시간 예산에서 유효한 기준안과 후보의 결과·위반 수·종료 이유·실제 시간을 비교한다. 읽기·전처리·탐색·결과 검사 중 포함한 시간을 밝히고 예상 복잡도와 실측을 구분한다. 작은 독립 정답으로 유효성을 먼저 확인하며, 항목 누락·제약 위반을 숨긴 속도나 기준값 0의 개선율을 만들지 않는다. 과제에 필요한 대표 규모부터 검사하고 비교용 알고리즘을 여러 개 만드는 일을 의무화하지 않는다.
- **예측 과제일 때만:** 예측 시점에 알 수 있는 정보, 시간·동일 개체가 섞이지 않는 분할, 학습 자료에서만 맞추는 전처리, 같은 조건의 단순 기준 방법과 실제 지표를 확인한다. 공식 평가용 자료를 방법 선택에 재사용하지 않는다. 회사명이나 CSV만 보고 예측 모델을 추가하지 않는다.
- **출력 파일:** 테스트가 소유한 새 임시 출력 경로에서 생성·내용·필수 형식을 확인한다. 예전 결과 파일이 남아 있는 것을 이번 실행 성공으로 세지 않는다. 유효한 0행 결과·중복 허용은 확인된 수락 조건을 따른다.

실행 명령·입력·기대/실제 결과·해당 범위를 기존 V와 check ID에 남긴다. 서로 다른 계산 방법이 일치해도 같은 잘못된 업무 가정을 공유할 수 있으므로 고객 확인을 대신하지 않는다.

## 입력 변경 뒤 결과가 맞는지 확인

업로드·설정 변경·재계산·캐시·비동기 처리가 실제 기능에 있을 때만 적용한다. 테스트 소유 자료와 실제 제품 API로 **입력 A → 계산/저장/조회 → 입력 또는 설정 B → 재계산 → B 기준 결과 조회**를 확인한다. 식별자만 보지 않고 관련 대상·값·조건·저장 내용을 대조한다. B 계산이 실패했거나 아직 진행 중이면 표시된 결과가 어느 입력 기준인지 구분한다. 결과가 우연히 같을 수 있으므로 무조건 출력이 달라져야 한다고 검사하지 않는다.

비동기 처리라면 제어 가능한 지연으로 B가 먼저 끝나고 A가 늦게 끝나는 순서를 재현해 옛 응답이 최신 결과를 덮지 않는지 확인한다. 캐시가 있으면 결과에 영향을 주는 자료·설정·코드/모델이 재사용 기준에 반영되는지 검사한다. 화면의 관련 상태는 제품이 쓰는 함수를 검사하고 최종 UI 목록에 모은다. 없는 결과 보존 정책·캐시·버전 체계를 새 필수 기능으로 만들지 않는다.

## 실행 틀과 단일 진입점

프로젝트의 기존 테스트·언어·실행 명령을 먼저 재사용한다. 없으면 제공 도구로 실행 가능한 Python unittest 또는 Node node:test를 선택한다. 새 테스트 프레임워크·브라우저 자동화·패키지 설치를 필수조건으로 만들지 않는다.

설치된 참조는 `.hackathon/testing/python/`와 `node/`다. `.example` 확장자는 자동 발견되지 않도록 남겨둔 것이다. 필요한 언어의 파일만 실제 프로젝트 `tests/` 등에 복사·이름 변경해 사용하고 기존 파일은 보존한다. 원본 준비 레포나 `.hackathon/` 참조를 직접 import하지 않는다. 실제 테스트/보조 코드가 실행 지문에 포함되게 한다.

- `http_fixture.*.example`: 임시 폴더와 테스트 소유 loopback 서버/HTTP 클라이언트. Python은 새 stdlib 호환 HTTPServer factory, Node는 새 node:http Server factory를 받는다. 다른 프레임워크에 기존 test client/fixture가 있으면 그것을 사용한다.
- `test_feature.py.example` / `feature.test.mjs.example`: 아직 과제를 모르는 스켈레톤. 기본은 skip이며 실제 테스트·기대값·생산 코드 연결을 작성한 뒤 활성화한다. skip 제거만으로 통과하지 않는다.

factory는 반드시 새 테스트 서버를 만들고 테스트가 만든 임시 저장소를 주입해야 한다. 참가자의 실행 서버·실제 DB를 반환하거나 임의의 다른 프로세스를 중지하지 않는다. 임시 파일 정리와 테스트 서버 종료는 성공/실패 모두에서 수행한다. 저장 보존 검사는 같은 임시 저장소로 서버를 다시 생성해 HTTP로 읽는다. 외부 서비스는 확인된 경계에만 대역을 쓰고, 핵심 제품 로직·내부 저장 흐름을 전부 mock하지 않는다.

프로젝트에 검증 진입점 하나를 정하고 실제 단위/API/업무 흐름/프런트엔드 검사가 그 명령에 포함되도록 한다. Python이면 기본 unittest discovery, Node면 실제 `package.json`의 test/verify 스크립트를 사용할 수 있다. 다음은 형식 예시이며 해당 프로젝트에 존재하는 명령/경로/R번호로 바꾼다.

```sh
python3 .hackathon/tools/kit.py check --workspace . --id feature-01 --requirement R-001 --test-runner unittest -- python3 -m unittest discover -s tests -v
python3 .hackathon/tools/kit.py check --workspace . --id feature-02 --requirement R-001 --test-runner node -- node --test --test-reporter=tap tests/feature.test.mjs
```

여러 R을 실제로 검사하면 `--requirement`를 반복한다. npm 등 wrapper는 `--test-runner node`를 명시하고 내부 runner가 TAP을 출력하게 한다. Node의 0건·전부 skip/todo는 NOT_RUN, 요약을 못 읽으면 UNVERIFIED다. 실패/cancelled를 출력한 wrapper가 0을 반환해도 통과로 보지 않는다. Node가 비어 있는 테스트 파일의 로드만 테스트 1건으로 보고할 수 있으므로 단순 import·실행 성공을 기능 검증이라고 해석하지 않는다. 이 키트는 assertion의 의미와 충분성을 자동 증명하지 않는다.

pytest도 출력된 모든 요약에서 실패를 보존한다. 요약이 여러 개면 성공/0건의 집계 범위를 확정할 수 없어, 실패가 있으면 FAIL·실패가 없으면 UNVERIFIED로 남긴다. 각 실행을 별도 check ID로 기록하거나 실제 테스트 한 번을 집계하는 명령을 쓴다. 실패 코드를 숨기는 실행 스크립트를 고쳐 통과 여부를 정확히 전달한다.

`expectedFailure`/`xfailed`는 아직 실패하는 것을 예상한 검사이며 일반 성공과 따로 센다. `xpassed`도 예상과 달라진 결과로 구분한다. 이들만 실행되면 실제 실행은 있었지만 기능 통과 근거는 부족하므로 UNVERIFIED다. 일반 성공과 섞여 실행 전체가 PASS여도 예상 실패가 남은 수락 조건을 Verified로 올리지 않는다.

소켓 실행이 막힌 환경에서는 허용된 단위/프로세스 내 API 검사를 진행하고 실제 HTTP는 미실행으로 구분한다. 가능한 범위와 실제 실행 결과를 남기고 제한을 우회하지 않는다. 테스트 작성/명령 실행은 Codex가 수행하므로 참가자가 중간마다 명령을 복사하거나 화면을 확인할 필요는 없다.

## UI 대기를 구현 중단으로 만들지 않기

기존 요구사항 행의 상태는 Implemented, 실제 결과는 자동 검사 PASS와 `check:<ID>`, 남은 문제는 최종 UI 확인 대기로 표시할 수 있다. 이는 기록 형식 예시이며 실제 결과가 있어야 한다. UI 수락 조건이 남으면 Verified로 올리지 않되 다음 독립 구현은 계속한다. 수락 조건 전체가 자동 검증 가능한 요구라면 그 실제 근거로 판단하며 모든 R에 불필요한 수동 UI 의무를 추가하지 않는다.

중간에는 참가자에게 각 기능의 클릭 검증을 요청하지 않는다. 자동 검증만으로 재현할 수 없고 다음 작업을 막는 구체적인 문제라면, 무엇이 막히며 어떤 최소 확인이 필요한지 설명한다. 고객 질문 중계와 주요 범위 결정은 계속 참가자가 맡는다. 첫 자동 검증된 핵심 흐름과 중요한 결정 변화에는 메인이 다음 대화에서 처리 흐름·기록된 선택의 장단점·검증 한계를 짧게 설명하고 다른 입력/선택을 본인 말로 설명할 질문 하나를 먼저 제안한다. 최종 UI 대기는 구분하되 R의 Verified 승격까지 설명을 미루지 않는다. 참가자가 미루거나 답을 기다려도 독립 작업은 계속하고 이해 확인 대기로 남긴다. 진행 중인 답 숨김 리허설의 미응답 내용을 먼저 설명하지 않으며 상세 기록은 기존 비공개 연습 기록을 쓴다.

## 빈 미리보기에서 원인을 좁히기

화면이 비거나 접속되지 않을 때만 아래 순서로 확인한다. 제공 도구와 허용된 로컬 HTTP를 쓰며 실제 앱·참가자 데이터를 보존한다.

| 확인할 곳 | 관찰과 다음 행동 |
| --- | --- |
| 프로세스·로그 | 실제 서버가 실행 중인지, 시작 실패·중단·승인 대기인지 확인. 기존 세션을 확인하기 전에 서버를 중복 실행하지 않음 |
| 실제 포트·바인딩 | 실행 로그의 실제 포트·경로와 `0.0.0.0` 바인딩 확인. 고정 포트·터널을 가정하지 않음 |
| HTML 경로 | 실제 문서 경로의 상태·내용 확인. 첫 페이지 HTTP 200만으로 화면 성공이라 하지 않음 |
| JS·CSS 경로 | HTML이 참조한 실제 자산의 상태·응답 종류 확인. JS 대신 HTML 200이면 잘못된 경로/폴백부터 확인 |
| API 경로 | 실제 응답 계약에 맞는 종류·값·오류 확인. JSON 경로의 HTML 200을 업무 성공으로 세지 않음 |
| 실제 화면 | HTTP 검사가 정상이어도 화면 동작은 미관찰로 남김. 다음 작업을 막는 경우만 최소 관찰을 요청하고 나머지는 최종 UI로 모음 |

`preflight --url`은 상태 코드 조회이며 본문·자산 검사를 대신하지 않는다. 필요한 응답 검사는 과제의 실제 테스트에서 수행하고 V/check로 연결한다. Host/Origin·프록시 주소를 추측하거나 허용 정책·감독 설정을 완화하지 않는다.

## 최종 UI 확인을 한 번에 모으기

1. 기능 동결 후 현재 코드·수락 조건·환경에 유효한 최종 자동 검사 근거를 확인·재사용하고 장부를 감사한다. 변경·실패·미검증 범위만 추가 검사하며 자동 통과 범위와 UI 대기를 구분한다.
2. 최종 코드로 실행 중인 과제 서버와 테스트용 서버를 구분하고, 실제 구현한 R번호별로 짧은 UI 확인 순서를 참가자에게 한 번에 전달한다. 각 단계에 실제 URL·입력·행동·기대 관찰·관련 R을 붙인다. 제안한 단계만으로 확인 완료라고 기록하지 않는다.
3. 참가자의 실제 결과를 받아 `manual-check`로 기록한다. 실제 화면의 핵심 흐름·검증 문구/피드백·새로고침/저장·읽기 어려운 표시를 과제에 맞게 확인한다. 브라우저 자동 조작은 수행하지 않는다.
4. 결함 수정 시 관련 자동 검사와 필요한 최종 회귀 검사를 재실행하고 영향을 받은 UI만 다시 확인한다. ‘최종 1회’가 수정 후 확인까지 생략한다는 뜻은 아니다.
5. 최종 코드/관찰을 기준으로 장부와 예상 문답을 갱신·검사한 뒤 참가자 복습·직접 제출 시간을 남긴다. UI를 기다리는 동안 문답 초안은 준비할 수 있지만, 미관찰 UI를 통과로 쓰지 않는다. 제출 확정 후 AI를 중단한다.
