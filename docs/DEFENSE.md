# Cofa Probe Q&A Defense Preparation

실제 구현을 설명하는 사전 학습용 기록이다. 공개 키트에는 이 빈 양식과 절차만 둔다. 과제 작업 공간에 설치된 `docs/DEFENSE.md`는 기본적으로 Git에서 제외한다. 원본 고객 대화·비공개 페르소나·인증정보는 복사하지 않고 공개 가능한 최소 요약과 Q/R/D/V·실행 ID만 연결한다. 이미 추적된 파일과 Git 이력은 ignore로 보호되지 않는다.

## 기능별 기록

아직 구현 기록 없음. 작은 사용자 흐름이 구현되고 자동 검증될 때 해당 절만 짧게 갱신한다. 최종 UI 확인이 남아도 자동 검증 범위와 대기를 구분해 기록한다. 코드·업무 규칙·검증 결과가 바뀌면 관련 설명도 고친다. 문서를 채우려고 개발을 중단하거나 리팩터링하지 않는다.

본문은 비개발자가 이해할 수 있도록 **사용자가 하는 일 → 프로그램의 처리 → 보이는 결과** 순서로 쓴다. 전문용어가 꼭 필요하면 처음에 쉬운 뜻을 붙인다. 함수명·파일·명령·실행 ID는 설명 뒤의 확인 근거로 연결하며, 쉬운 설명을 위해 실제 예외·실패·미검증 범위를 생략하지 않는다.

기존 요구사항 정본, `.hackathon/DECISIONS.md`, `.hackathon/VERIFICATION.md`가 상세 근거다. 아래 항목은 기능당 몇 줄의 색인으로 쓰며 같은 장부를 다시 만들지 않는다. 아래는 **빈 형식**이며 요구·고객 답변·결정·실행 결과가 아니다.

고객이 해결하려던 문제·전체 업무 흐름·첫 MVP와 최종 필수 범위는 요구사항 정본의 요약을 참조한다. 각 설명은 실제 R·코드·검증과 대조하고, 필수 요구의 구현/검증 상태·미확인·미완료는 해당 R에서 확인한다. 이 파일에 PRD나 상태 표를 복제하지 않는다.

```text
### <실제 사용자 흐름 이름> · <관련 R ID>
- 사용자 관점: <누가 무엇을 하면 어떤 결과를 얻는지 쉬운 한 문장>
- 처리 흐름: <사용자 입력 → 확인하는 내용 → 프로그램이 처리·저장하는 일 → 화면/파일 결과>
- 코드 위치(확인 근거): <실제 상대 경로:행 · 핵심 함수/호출 관계>
- 업무 규칙: <고객/공식 확인 R·Q·과제 위치> / <자체 설계 D·ADR> / <미확인 사항>
- 예외·장애: <실제로 구현된 경계 조건·오류 응답·복구, 미구현은 따로 표시>
- 자체 선택과 대안: <해결하려던 문제, 채택 이유와 당시 고려·기각한 대안, D/ADR 참조>
- 선택의 장단점: <얻은 점·감수한 점과 조건이 달라지면 다시 고를 기준, 기록된 D 참조>
- 중요한 판단: <D 참조 · AI 제안 · 실제 결정 주체/선택 · 당시 밝힌 이유 · 결과/재확인>
- 검증: <실제 작은 입력 → 기대 결과·근거 R/Q/D → 관찰 결과 → 제품 함수와 실제 테스트의 확인문(assertion)> / <V·check/manual ID · 실제 명령/관찰 절차 · PASS/FAIL/NOT_RUN/UNVERIFIED · 검증 범위>
- 한계: <미검증 조건·남은 UI 확인·알려진 실패·후순위 개선>
```

고객이 정한 정책, 개발자에게 맡긴 범위 안의 자체 선택, 아직 답을 못 받은 업무 사항을 구분한다. 위임받은 선택은 Q·범위·제약과 D를 참조해 ‘고객이 방법을 맡겨 우리가 이 이유로 선택했다’고 설명한다. 이를 고객이 해당 정책을 요청했다거나 미확인이라 계속 보류해야 한다는 뜻으로 바꾸지 않는다. 위임되지 않은 미확인 정책은 ‘임시 가정/미확인’으로 남기고 중요한 업무 결과는 질문한다. 당시 이유가 없으면 ‘당시 이유 미기록’, 뒤늦은 설명은 ‘현재 코드로 해석’으로 구분한다. 실제로 고려하지 않은 대안은 만들어내지 말고 미기록으로 남긴다.

참가자의 실제 개입·수정 사건은 기존 D를 참조하고 AI 자율 판단과 구분한다. 실제 사건이 없는 항목은 채우지 않는다. 자료 과제라면 결과 숫자가 어떤 자료·기간·계산 대상에서 나왔는지 해당 R/V를 연결한다.

`domain-modeling`의 용어집과 ADR 규칙은 유지한다. 용어는 GLOSSARY, 일반 선택은 기존 D 기록에 둔다. 되돌리기 어렵고, 맥락 없이 의외이며, 실제 대안 간 절충이 있었을 때만 Matt 형식의 ADR을 제안한다. DEFENSE에는 해당 결정을 참조한다.

확인문(assertion)은 기대값과 실제값을 비교하는 테스트 구문이다. 실제로 무엇을 비교했는지 짚고, 수동 관찰만 했다면 자동 확인문이 없다고 적는다. 관찰하지 않은 결과는 ‘코드 해석/미실행’ 또는 ‘UI 미관찰’로 표시한다. 검증 명령은 실제 실행 기록에서 가져오고 실패·미실행·오래된 결과를 성공으로 설명하지 않는다. 실패를 수정하면 원래 절차를 새 ID로 재실행해 전후 결과를 연결한다. 기록 전 함수·행·분기·상태와 테스트를 직접 읽어 설명을 대조한다. `audit-requirements`와 `verify-qa`는 구조·참조·최신성 검사이며 자연어 설명이나 참가자 이해의 정답 판정기가 아니다.

## 개발 중 이해 확인

첫 자동 검증된 핵심 흐름과 중요한 결정 변화는 메인이 다음 유용한 대화에서 작은 실제 입력 한 건으로 입력→기대 결과와 근거→관찰 결과→제품 함수·실제 테스트의 확인문을 이어 설명한다. 고객 기준과 자체 선택, 기록된 선택의 장단점·한계와 최종 UI 대기도 짧게 알린다. 이어 다른 근거 있는 작은 입력에 대해 같은 연결과 선택 이유를 본인 말로 설명할 질문 하나를 제안한다. 미관찰 결과는 예상임을 밝히게 한다. 기능마다 새 문답이나 승인 관문을 만들지 않고 참가자가 연기하거나 답을 기다리는 동안 독립 작업은 계속한다.

먼저 기존 `.hackathon/study/DEFENSE_REHEARSALS.md`의 답 숨김 회차를 확인한다. 미응답 리허설이 있으면 관련 답·힌트를 설명하지 않고 기존 모드를 유지한다. 개발 중 질문은 같은 파일의 짧은 별도 절에 질문 시점·R/D/코드 근거와 실제 받은 응답·피드백·대기/연기만 보존하고, 5문항 회차나 `qa.json`을 새로 만들지 않는다. 이 빈 공개 양식에는 응답을 채우지 않는다. 실제 응답 뒤 코드·검증과 대조하고 오해가 있으면 필요한 흐름만 보충한 뒤 다른 입력으로 다시 설명하게 한다. 설명을 읽었거나 자동 검사가 통과했다는 이유로 이해 완료를 기록하지 않는다. 실제 AI 금지 평가와 AI 중단 시점에는 이 절차를 수행하지 않는다.

## Q&A 리허설 시작

참가자가 **“Q&A 리허설 시작”**이라고 하면 `$implementation-brief`의 [리허설 절차](../.agents/skills/implementation-brief/references/defense-rehearsal.md)를 따른다. 현재 구현을 조사해 질문 5개를 먼저 보여주고 답변을 기다린다. 기존 정답 포함 복습과 구분한다. 실제 AI 금지 평가에서는 이 모드를 사용하지 않는다.

질문·회차·당시 근거·미응답 상태는 기존 Git 제외 `DEFENSE_REHEARSALS.md`에 먼저 남기며 이 빈 양식에 답을 채우지 않는다. 세션 재개에서도 답 숨김을 유지하고, 질문 후 관련 구현이 바뀌면 해당 문항은 평가를 보류해 새 전제로 다시 묻는다.

오답 뒤 이해가 막힌 흐름만 같은 실제 입력 한 건으로 3~5단계 따라간다. 값의 변화와 실제 함수·파일을 연결하되, 실행 관찰·코드 해석·미확인을 구분한다. [보충 학습 절차](../.agents/skills/implementation-brief/references/defense-rehearsal.md#보충-학습답변-후)에 따라 설명 뒤 다른 입력으로 본인 설명을 다시 받는다. 원문 응답은 기존 Git 제외 복습 영역에 두고 이 파일에는 필요한 흐름 요약·근거만 남긴다.
