# 요구사항과 실행 근거 연결

기록은 구현을 설명하고 누락을 찾기 위한 도구다. Markdown 작성이나 스킬 호출이 공식 점수를 보장하지 않으며, 평가기가 이 문서를 읽는다고 가정하지 않는다. 매 답변·작동 흐름·실행 후 바뀐 항목만 짧게 갱신한다. 별도 PRD·티켓·Evidence 저장소를 새로 만들 필요는 없다.

## 기존 문서를 기준으로 연결

이 키트에서는 `.hackathon/REQUIREMENTS.md`가 요구사항의 단일 장부다. 이미 다른 요구사항 문서가 있으면 그것을 사용하고 중복 작성하지 않는다. 아무 문서도 없는 수동 적용 프로젝트만 `docs/REQUIREMENTS.md`를 만든다. 기존 ID는 유지한다.

각 요구사항에서 다음을 찾을 수 있어야 한다. 긴 내용은 기존 결정·검증 장부의 D/V 번호로 연결해도 된다.

| 항목 | 기록할 내용 |
| --- | --- |
| Requirement ID / Description | 유지되는 R 번호, 한 가지 관찰 가능한 요구 |
| Customer Evidence | Q 번호·질문/실제 답변 위치 또는 공식 과제 위치. 요약·가설·공식 조건을 구분 |
| Status | Proposed / Confirmed / Implemented / Verified / Blocked |
| Acceptance Criteria | 입력·행동·관찰할 결과와 중요한 제외/경계. 필요한 수동 확인도 명시 |
| Design Decision | 중요한 선택의 D 번호·이유·대안·한계. 없으면 해당 없음 |
| Implementation Files | 존재하는 파일·필요할 때 함수/행. 계획 경로는 계획이라고 표시 |
| Verification Procedure | V 번호 또는 실제 명령·테스트 이름·수동 절차·기대 결과 |
| Actual Verification Result | 실제 실행 기록 경로·성공/실패·관찰 결과·검증 범위. 미실행은 미실행 |
| Remaining Issues | 남은 질문·미구현/미검증·알려진 실패 조건. 없다는 주장에도 근거가 필요 |

우선순위와 근거도 기존 장부에 유지한다. 한 셀에는 짧은 요약과 참조를 쓴다. 설계 이유는 DECISIONS, 실행 상세는 VERIFICATION에 한 번만 적는다.

## 상태의 의미

- **Proposed**: 가설 또는 미확인 제안. 고객 사실로 확정하지 않는다.
- **Confirmed**: 실제 고객 답변이나 공식 필수조건으로 확인. 후순위·범위 제외 요구도 Confirmed로 두고 범위를 따로 적는다.
- **Implemented**: 확인된 요구의 구현 파일이 존재하나 수락 조건 전체의 검증은 남음. 일부 구현이면 Confirmed와 부분 구현 내용을 남긴다.
- **Verified**: 해당 수락 조건 전체에 실제 검증 결과가 연결됨. 테스트 일부의 통과, 구문 검사, 질문 제안만으로 승격하지 않는다. 화면 확인이 수락 조건인데 결과가 없으면 Implemented다.
- **Blocked**: 필요한 답변·환경 등으로 진행이 막힘. 기존 확인 근거와 마지막 구현/검증 상태, 차단 이유를 보존한다. 독립 작업까지 중단하지 않는다.

코드·수락 조건·입력·환경이 바뀌거나 실패가 발견되면 관련 Verified를 재검토한다. 과거 통과는 이력으로 유지하고 현재 상태는 재검증 전으로 돌린다. 제안을 몰래 구현하거나 테스트가 있다는 이유로 고객 확인을 생략하지 않는다.

## 매 단계의 행동

인터뷰 뒤 실제로 전달받은 질문·답변에 Q 번호를 붙이고 확인된 사실과 가설을 구분한다. R 번호·수락 조건을 갱신하고, 구현을 바꾸는 중요한 미확인은 다음 고객 질문으로 제안한다. 과거에 질문 원문이 없으면 답변만 있다고 적고 질문을 소급 창작하지 않는다.

설계·구현할 때 관련 R 번호를 먼저 밝힌다. 중요한 선택만 기존 DECISIONS에 R/D 번호·이유·기각 대안·한계·관련 파일로 남긴다. 사후에 정리한 이유를 당시의 의사결정 기록이라고 주장하지 않는다. 모든 커밋·코드 행에 ID를 붙일 필요는 없다.

검증할 때 R 번호와 테스트/수동 절차를 연결한다. 명령·입력·기대·실제 결과·성공/실패·한계를 VERIFICATION에 남긴다. 자동 실행은 기존 `kit.py check`로 원본을 보존할 수 있다. 수동 결과는 관찰자와 실제 관찰 내용을 적고 Codex가 직접 화면을 봤다고 쓰지 않는다. 실패를 고치면 원래 실패 절차를 재실행하고 두 기록을 연결한다. 과거 로그가 없으면 없다고 적는다.

완료 보고는 **구현됨 / 실제 검증됨 / 미확인 또는 미구현 / 알려진 실패 조건** 네 가지로 짧게 한다. 모르는 실패 범위를 ‘없음’으로 단정하지 않는다. 문답 생성은 이 R→D→파일→V 연결을 재사용하고 비공개 원문을 복습본에 불필요하게 복사하지 않는다.

필요한 스킬만 선택한다. Matt 원본 SKILL.md는 수정하지 않는다. 자동/명시 호출 방식은 기존 SKILLS 안내와 설치된 메타데이터를 따른다.

## 비공개 원문과 공개 경계

고객 질문·답변 원문은 `.hackathon/private/INTERVIEWS.md`에 Q 번호로 저장한다. 이 위치는 **참가자가 전달한 답변**을 보관하는 곳이며 비공개 페르소나·숨은 평가표를 개발 공간에 가져오는 용도가 아니다. 요구사항에는 최소 요약과 Q 참조만 남긴다. 원문·자료에 인증정보가 있으면 복사·로그 저장부터 피한다.

설치기는 `.gitignore`에 `.hackathon/private/`, 실행 원본 `checks/`, 복습본 `study/`, 운영자 자료용 루트 `private/`, `PRIVATE*`를 제외한다. 기존 ignore 규칙과 파일은 보존한다. 기존 추적 파일은 ignore로 보호되지 않으므로 설치 시 해당 경로의 추적 파일이 있으면 쓰기 전에 중단한다. 이미 커밋된 원문은 파일 이동·ignore만으로 Git 이력에서 없어지지 않는다. 이력이 발견되면 공개하지 말고 경로와 사실을 사용자에게 알린다. 이력 재작성·원격 조작은 자동 수행하지 않는다.

요구사항 요약·용어집·결정·코드·합성 자료도 자동으로 공개 허용되는 것은 아니다. 공개 준비 키트에는 일반 규칙·빈 양식·명시적 예시만 넣는다. 실제 고객 정보가 있는 프로젝트는 공개 허용 범위를 검토하고 사용자의 별도 승인 후 공개한다. 시험 중 외부 전송 금지는 그대로 적용한다. ignore는 Git 실수 방지이며 접근 통제나 비밀 탐지기가 아니다.

## 형식 예시 — 실제 고객/프로젝트 근거 아님

아래 내용은 모두 가상 예시다. 실제 답변·구현·실행 결과로 장부에 등록하지 않는다.

```text
EXAMPLE-Q1 질문: 숫자 두 개를 입력하면 어떤 결과가 필요하나요?
EXAMPLE-Q1 답변(가상): 두 수의 합을 보여주세요.
EXAMPLE-R001: 두 수의 합 반환 / Confirmed
수락 조건: 2와 3을 입력하면 5, -2와 2는 0.
근거: .hackathon/private/INTERVIEWS.md의 EXAMPLE-Q1
설계: 내장 덧셈 사용, 외부 서비스 불필요(예시 선택).
구현 파일: demo_total.py(가상 경로, 생성 전에는 계획)
검증 절차: unittest로 위 두 사례 확인(예시 계획)
실제 결과: 미실행. 이 안내만 읽고 Verified로 바꾸지 않음.
남은 항목: 구현·실행 필요, 숫자 외 입력 범위 미확인.
```

실제 흐름 점검은 격리한 임시 공간에서 이 예시를 구현·실행하고 실행 원본을 확인한다. 그 결과는 ‘예시 연결 점검’이며 고객 기능이나 실제 요구사항의 검증으로 세지 않는다.
