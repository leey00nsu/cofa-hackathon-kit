# 메인이 운영하는 병렬 작업과 고객 피드백

작업을 나누거나 배정받았을 때 읽는다. 참가자는 메인과 대화하고 고객 질문·답변을 중계한다. 메인이 작업 배정·진행 확인·질문 취합·답변 전달·결과 검토·통합을 맡는다. 이 문서는 실행 기능이나 파일 잠금을 추가하지 않으며, 실제 제공 도구와 대회 규칙 안에서 적용하는 절차다.

## 역할과 실행 수단

- **메인:** 관련 Q/R과 성공 조건을 정리하고 독립 작업을 배정한다. 고객 원문, R/D/V, GLOSSARY·ADR·DEFENSE의 최종 기록, 공용 설정·의존성·통합 서버와 최종 검증을 관리한다. 질문과 결과를 기다리는 동안 직접 맡은 핵심 작업도 진행한다.
- **작업자:** 배정된 코드와 그 기능의 테스트를 맡는다. 중요한 자체 선택·새 업무 질문·실제 실행·한계를 메인에게 돌려준다. 공용 장부를 직접 갱신하거나 참가자에게 별도로 질문하지 않는다.
- **검토자:** 배정된 변경과 근거를 읽고 문제·누락·위치를 메인에게 보고한다. 읽기 전용 검토에는 제품 파일 수정과 통합 서버 재시작을 포함하지 않는다. 끝난 작업자를 새 범위의 검토자로 다시 쓸 수 있다.

메인은 현재 도구를 확인해 다음 중 가능한 수단을 선택한다. 참가자에게 작업 분배나 일반적인 실행 승인을 반복해서 맡기지 않는다.

1. **내장 서브에이전트:** 실제 생성·메시지·상태 확인 도구가 있으면 우선 사용한다. 독립 작업을 배정하고 결과를 취합한다. 사용 가능하다고 추정하거나 도구 이름을 만들어내지 않는다.
2. **제공된 Codex CLI:** 내장 수단이 없고 로컬 CLI 병렬 실행이 허용되면 메인이 CLI 작업을 직접 시작·확인·회수한다. 제공된 `codex --version`과 `codex exec --help`로 필요한 기능만 확인한다. 같은 제공 인증·허용 모델·권한을 사용하며 업데이트·개인 키·외부 모델·설정 변경·권한 우회로 병렬 기능을 만들지 않는다.
3. **메인의 단독 진행:** 둘 다 사용할 수 없으면 실제 제한을 짧게 알리고 확인된 작업을 직접 계속한다. 실행하지 않은 작업을 서브가 진행 중이라고 보고하지 않는다.

처음에는 독립 작업 2개 정도로 시작하고 실제 시간·자원·제공 한도에 맞춰 조정한다. 작은 수정이나 순서상 바로 의존하는 작업은 메인이 맡는다. 서브가 다시 하위 작업자를 늘리지 않으며 필요한 추가 분할은 메인이 조정한다.

## 배정하고 진행하기

1. **연결할 부분을 먼저 정한다.** 입력·출력·오류 형식과 관련 R의 성공 조건을 최소한으로 맞춘다. 메인은 요구사항의 기존 ‘구현 진입 판단’에 처리·분기 순서, 핵심 방법·연결, 오류 처리, 선택 이유·실제 대안 D와 검사 방법을 몇 줄로 정리하고 배정에 참조한다. 모든 상세 설계를 끝낼 필요는 없다. 확인되지 않은 업무 규칙을 구현 편의상 정하지 않는다.
2. **독립적으로 구현·검사할 크기로 나눈다.** 각 작업자가 실패하는 테스트 → 최소 제품 구현 → 실제 실행·수정·재검증을 맡는다. 무조건 함수 단위로 쪼개거나 구현과 테스트를 서로 의존하는 별도 작업으로 분리하지 않는다. 필요한 `implement`/`tdd`를 지시에 명시하고 호출이 없으면 원본 절차를 읽어 적용한다.
3. **담당을 겹치지 않게 배정한다.** 제품 파일·테스트 파일마다 작성자는 하나다. 공용 설정·패키지와 잠금 파일·DB 구조·공유 환경 변경은 메인에게 요청한다. 같은 작업 폴더의 Git 전환·스테이징·커밋은 메인만 한다. 이는 작업자의 Matt `implement` 커밋 단계에도 적용한다. 메인이 별도 Git 작업 폴더와 해당 브랜치 커밋을 명시한 경우만 그 범위에서 수행한다.
4. **작업과 전달 근거를 짧게 남긴다.** 기존 인계나 작업 기록이 있으면 재사용한다. 없으면 메인 소유의 Git 제외 `.hackathon/study/parallel.md`에 작업 이름, 담당·실제 세션/프로세스 식별자, R/Q/D 참조, 수정 파일, 현재 진행/질문 대기/반환 여부, 최신 지시·결과 경로만 적는다. 이는 요구사항·결정 장부가 아니며 새 상태 체계나 별도 일정 도구가 필요하지 않다.
5. **메인도 독립 작업을 계속한다.** 배정 직후 결과만 기다리거나 같은 작업을 다시 구현하지 않는다. 필요한 시점에 실제 상태·출력을 확인하고 막힌 지점을 해결한다. 지시·결과 파일을 쓴 것만으로 작업 시작·수신·완료를 가정하지 않는다.

다음은 빈 지시 형식이다. 실제 배정에 필요한 항목만 사용하며 원문 대화·비공개 페르소나·평가표·인증정보를 복사하지 않는다.

```text
역할/작업 이름: <작업자 또는 검토자, 실제 작업 이름>
작업 공간·기준: <정확한 경로, 현재 R/Q/D 참조, 지시 시점 또는 회차>
목표·성공 조건: <사용자 입력 → 처리 → 결과, 오류 조건>
수정 범위: <제품·테스트 파일, 공용 파일 담당은 메인>
연결 방식: <주고받는 값·오류와 다른 담당자의 경계>
로직 전략: <기존 구현 진입 판단·관련 D, 처리 순서와 지켜야 할 조건>
미확인/위임: <답을 못 받은 업무 사항, 개발자에게 맡긴 범위·제약>
운영: <시간 범위, 질문·실행·결과를 돌려줄 수단과 정확한 경로>
반환: <실제 변경·실행 근거·중요한 선택·질문·미완료·한계>
```

## 서브 질문을 고객 답변까지 연결하기

1. **작업자는 의문을 메인에게 보낸다.** 질문, 어떤 입력/코드/테스트에서 발견했는지, 관련 R과 기존 근거, 답에 따라 달라지는 결과, 지금 막힌 부분과 계속할 수 있는 부분을 짧게 전달한다. 임의의 고객 답변·성공 결과를 만들지 않는다. 고객 챗봇이나 숨은 자료에 직접 접근하지 않는다.
2. **메인은 기존 사실과 결정 권한을 먼저 확인한다.** 이미 답한 내용은 해당 Q/R을 작업자에게 전달한다. 기술 선택이나 고객이 명확히 맡긴 선택은 제약 안에서 처리하고 중요한 선택을 D에 남긴다. 실제 고객 확인이 필요한 새 업무 질문만 중복을 합쳐 참가자에게 전달한다. 중요한 질문을 다른 작업자 전원의 완료까지 미루지 않는다. 한 번의 질문 묶음은 전체 라운드 제한이 아니다.
3. **대기 범위를 좁힌다.** 필요한 답을 얻기 전에는 그 규칙에 의존하는 구현·검증만 보류한다. 해당 작업자의 독립 부분, 다른 작업자, 메인의 다른 작업은 계속한다. 서브의 추측을 고객 확인으로 쓰지 않는다.
4. **실제 중계 답변을 같은 기록에 반영한다.** 메인이 실제로 전달한 질문과 받은 답변을 Q로 보존하고 기존 요약·관련 R·수락 조건·필요한 D를 갱신한다. 작업자가 제안한 질문과 실제 고객에게 전달한 질문이 다르면 구분한다.
5. **관련 작업자에게 변경을 명시적으로 전달한다.** 새 Q, 변경된 R/조건, 유지할 제약, 영향받는 파일·테스트와 재개할 범위를 보낸다. 새 지시가 도착했다는 응답이나 실제 결과로 반영 여부를 확인한다. 진행 중인 세션이 수정된 파일을 자동으로 다시 읽는다고 가정하지 않는다. 변경 전 근거의 결과는 이력으로 남기며 바뀐 전제의 검증으로 재사용하지 않는다.
6. **같은 루프를 반복한다.** 구현 중 새 예외·모순이 나오면 다시 확인한다. 필요한 고객 질문은 메인이 참가자에게 전달하고, 참가자에게 작업자 세션을 직접 관리하게 하지 않는다.

## 별도 CLI로 운영할 때

CLI는 별도 대화이므로 메인의 대화가 자동 공유된다고 가정하지 않는다. 메인이 현재 지시와 작업별 결과·실행 로그 경로를 Git 제외 `.hackathon/study/` 아래에 준비한다. 파일 이름은 작업과 회차별로 달리해 기존 질문·실패·결과를 덮어쓰지 않는다. 공용 기록은 메인이, 각 작업 결과는 해당 작업자만 쓴다.

다음은 **도움말에서 옵션 지원을 확인한 뒤 쓰는 명령 형식 예시**다. 메인이 실제 지시 파일을 만든 후 과제 작업 공간에서 실행한다. 두 번째 작업은 다른 작업 이름·결과/로그 경로로 시작한다.

```sh
codex exec -o .hackathon/study/worker-a-result-01.txt - < .hackathon/study/worker-a-task-01.txt > .hackathon/study/worker-a-run-01.log 2>&1
```

- 메인의 터미널 도구가 제공하는 백그라운드 실행·세션 핸들로 작업을 유지하고 실제 종료 코드·로그·결과를 회수한다. 여러 작업을 시작할 수 있다는 것과 실제로 동시에 실행됐다는 것은 구분한다. 지원되지 않으면 실행 가능한 범위로 줄인다. 작업자 실행이 0으로 끝나도 기능 성공으로 해석하지 않는다.
- 대화형 질문 도구를 참가자에게 직접 띄우지 않는다. CLI 작업자가 답을 기다려야 하면 질문과 미완료·독립 작업 결과를 반환하고 해당 실행을 끝낸다. 메인은 질문을 중계한 뒤 갱신된 지시로 다시 실행하거나, 지원되는 정확한 세션 ID로 이어간다. 여러 작업이 있으므로 `--last`로 대상을 추정하지 않는다.
- 실행 중인 CLI에 새 규칙을 보낼 수 있는 수단이 있으면 확인 응답을 받는다. 없으면 그 실행의 종료/중단을 확인한 뒤 새 지시로 재개한다. 이전 작성자가 계속 실행 중인 파일을 다른 작성자에게 재배정하지 않는다. 세션이 멈췄다고 가정하거나 일괄 프로세스 종료 명령을 쓰지 않는다.
- 원래 환경의 권한·승인 제한 때문에 실행할 수 없으면 실제 실패로 남기고 메인이 독립 작업을 계속한다. 새로운 인증이나 우회 옵션을 추가하지 않는다. CLI 출력 파일은 기능 검증 근거의 원본 로그를 대체하지 않는다.

별도 Git 작업 폴더를 쓰는 경우 메인이 정확한 기준·작업 경로·반영 방법과 필요한 지침을 전달한다. Git 제외 기록이나 미추적 코드가 자동 복사된다고 가정하지 않는다. 허용된 경로와 자료만 필요한 범위에서 준비하며, 폴더 분리만으로 공유 패키지·포트·DB·설정까지 분리됐다고 말하지 않는다.

## 결과 검토·통합과 마무리

작업자는 기준 R/Q/D·지시 회차, 실제 변경 파일·처리 흐름, 실행 명령·check ID/로그·관찰 결과, 중요한 선택과 당시 이유, 새 질문·미완료·한계를 몇 줄로 반환하고 상세는 실제 파일·로그를 참조한다. 보고서만으로 업무 규칙 확인이나 요구사항 Verified를 선언하지 않는다. 작업 중 `kit.py check`를 쓰면 메인이 지정한 작업별 고유 ID를 쓰고 공용 R/D/V는 수정하지 않는다. 기록기가 막히면 실제 오류·명령·종료 코드·출력을 담당 보고/로그에 보존해 메인에게 돌려준다. 독자적인 기록을 kit 호환 check라고 등록하거나 실패를 성공으로 바꾸지 않는다.

메인은 반환 기준을 현재 고객 답변·지시와 대조하고 실제 코드·테스트·실행 기록을 읽는다. 범위를 벗어난 변경, 빠진 수락 조건, 아직 답을 못 받은 정책, 개발자 선택을 고객 요구로 표현한 부분을 확인한다. 변경 중인 공유 소스에서 실행됐거나 다른 작업 폴더에서 얻은 결과는 적용 가능성을 별도로 확인한다. 기존 지문·근거 검사를 느슨하게 바꾸지 않는다.

작성 담당의 종료/반환과 파일 변경 범위를 확인한 뒤 통합하고 안정된 실제 소스에서 필요한 연결·회귀 검사를 수행한다. 관련 변경으로 오래된 검증만 다시 실행하고 현재 유효한 결과는 재사용한다. 메인이 기존 R/D/V·DEFENSE를 짧게 갱신하며, 자동 검사 통과와 최종 UI 확인 대기를 구분한다. 검토자를 재사용할 때도 새 역할·읽기 범위를 명확히 전달한다.

첫 흐름과 중요한 규칙·로직 변경 뒤에는 기존 리뷰의 요구사항 대조에서 빠진 반례를 찾도록 배정한다. 실제 R/Q/D·코드·테스트를 읽고 구체적인 입력/행동, 기대 근거 또는 업무 질문, 검사 누락과 실제 관찰/미실행을 반환하게 한다. 메인은 업무 질문을 중계하고 실제 결함은 현재 작성 담당에게 실패 테스트·수정·재검증으로 돌려준다. 검토자가 직접 코드를 고치거나 제안만으로 통과를 기록하지 않는다. 독립 검토자가 없으면 메인의 자체 검토로 표시하고 같은 기록에 남긴다. 상세는 [자동 검증의 반례 검토](../AUTOMATED_TESTING.md#첫-흐름-뒤-빠진-반례-검토)를 따른다.

첫 자동 검증된 핵심 흐름과 중요한 D 변화는 메인이 참가자에게 쉬운 처리 흐름·실제 선택의 장단점·검증 한계를 설명하고 본인 설명 질문 하나를 먼저 제안한다. 작업자가 참가자에게 직접 묻지 않으며 미응답·연기 중 다른 작업은 계속한다. 답을 가린 리허설이 대기 중이면 해당 내용을 먼저 설명하지 않는다. 실제 응답·피드백만 기존 비공개 연습 기록에 보존하며 최종 Q&A까지 이해 확인을 전부 미루지 않는다.

마감 전에는 새 배정을 줄이고 진행 중인 실행과 미완료를 회수·확인한다. 최종 검사·문답·리허설의 근거가 바뀌지 않도록 관련 작성자를 정리한 뒤 실제 구현 기준으로 복습을 준비한다. 참가자는 최종 UI와 직접 제출을 맡는다. AI 중단 시점 이후 작업자가 계속 실행되지 않도록 메인이 담당 실행의 종료·중단 결과를 확인하고, 확인하지 못한 상태는 그대로 알린다. 실제 AI 금지 Q&A에는 메인·서브 모두 도움을 제공하지 않는다.
