# 고객 인터뷰와 구현 전환

고객 사실은 참가자가 중계한 답변과 공식 과제에서 확인한다. 기술적 선택은 Codex가 판단한다. 질문 횟수를 채우거나 전체 설계를 끝낼 때까지 기다리는 대신, 다음 구현 결정을 바꾸는 불확실성을 우선 해소한다.

프로젝트 AGENTS의 Evidence 규칙에 따라 질문·실제 답변 원문은 Git 제외 `.hackathon/private/INTERVIEWS.md`에 Q번호로 보관하고, 기존 요구사항 장부에는 사실/가설·R번호·Q참조·관찰 가능한 수락 조건을 남긴다. 문서 수와 질문 수를 늘리는 절차로 만들지 않는다.

## 전체 문제와 첫 흐름을 정리하기

첫 구현 전에 기존 요구사항 정본의 ‘문제와 첫 흐름 요약’을 아는 만큼 짧게 정리한다. 기존에 같은 역할을 하는 절은 재사용한다. 누가 어떤 불편을 겪고 무엇이 좋아져야 하는지, 주요 업무의 입력부터 완료까지 큰 그림을 설명하고 첫 구현 흐름과 관련 R을 선택한다. 실제 규칙·제약·성공/실패 기준은 R에 두고 요약에서 참조한다. PRD라는 이름의 새 파일이나 중복 표는 필요 없다.

전체 목적을 이해하는 것과 모든 상세 규칙을 확정하는 것은 다르다. 첫 흐름을 바꿀 미확인에 집중하고 나머지는 영향과 함께 남긴다. 받은 자료에 명확한 내용은 반복 질문하지 않는다. 요약 작성·버전명·빈칸 채우기를 구현 대기 조건으로 삼지 않는다. 처리 속도·기록 보존 기간 같은 조건도 실제 과제·답변 근거가 있는 중요한 것만 R에 연결한다.

## 자료가 있는 과제에서 먼저 확인할 뜻

실제 제공 파일을 읽기만 하여 열 이름·행 수·일부 안전한 예시·빈 값·반복 식별자를 확인한다. 원본을 고치거나 자료 전체를 대화에 붙이지 않는다. 자료가 의미하는 업무 기준은 다음 중 해당하는 것만 고객에게 묻는다.

- **한 줄과 식별자:** 한 줄은 주문 한 건인가, 품목 한 개인가, 재검사 한 번인가? 여러 열을 합쳐 구분하는가? `001`과 `1`, 공백·대소문자를 같은 값으로 볼지는 임의로 정하지 않는다.
- **반복과 누락:** 같은 번호의 여러 행은 정상 반복인가, 중복인가? 빈 값은 미입력인가, 실제 0인가? 제외·수정·보류 중 어떤 처리가 맞는가?
- **숫자와 기간:** 수량·금액·비율의 단위와 계산 대상은 무엇인가? 비율의 분자·분모, 재검사 포함 범위, 날짜 양끝 포함 여부와 시간대는 무엇인가?
- **자료 결합:** 어떤 열로 연결하며 한 건에 여러 건이 연결되는 것이 정상인가? 연결되지 않은 항목과 결합 후 늘어난 행을 어떻게 처리하는가?

파일에서 관찰한 사실과 고객이 정한 뜻을 구분한다. 중요한 미확인은 다음 질문으로 제안하고 독립 작업을 이어간다. 확인한 내용은 관련 R의 설명·근거·수락 조건·남은 질문에 짧게 연결한다. 별도 데이터 계약 장부나 모든 항목을 채우는 의무는 만들지 않는다.

## 여섯 영역의 확인 상태

`.hackathon/REQUIREMENTS.md`의 탐색 표를 매 답변마다 갱신한다. 상태는 `확인`, `부분확인`, `미확인`, `해당없음`으로 구분한다. 확인에는 질문 번호 또는 공식 과제의 근거를 붙인다. 해당없음은 확인된 범위로 설명할 수 있어야 하며, 아직 묻지 않았다는 뜻으로 사용하지 않는다.

| 영역 | 확인할 내용 | 열린 질문 예시 |
| --- | --- | --- |
| 현재 업무 흐름 | 담당자·시작·실제 처리·업무 완료 | 최근 한 건을 처음부터 끝까지 처리한 과정을 설명해 주세요. |
| 입력과 결과 | 자료 출처·입력 항목·결과·남겨야 할 기록 | 어떤 자료로 시작하며, 처리가 끝나면 무엇이 남아 있어야 하나요? |
| 판단 기준 | 대상·제외·경계·상태·시각 기준 | 어떤 경우에 처리하고, 비슷해 보여도 처리하지 않는 경우는 무엇인가요? |
| 사람의 판단과 권한 | 사람이 확인할 일·자동으로 할 일·금지 행동 | 직원 확인이 필요한 행동과 도구가 자동으로 해도 되는 행동을 알려주세요. |
| 예외와 기록 보존 | 오류·결측·반복 입력·중단·다시 시작 | 잘못된 자료나 반복 작업이 생기면 어떻게 처리하며 무엇이 보존돼야 하나요? |
| 우선순위와 성공 | 필수·후순위·범위 제외·관찰 가능한 성공 | 이번에 가장 먼저 해결할 일과 미뤄도 되는 일은 무엇이며, 어떻게 성공을 확인하나요? |

표의 예시를 그대로 전부 묻지 않는다. 이미 답한 것은 재사용하고, 실제 고객의 용어와 사례에 맞춰 한 번에 전달할 1~3개 질문만 제안한다. 이는 전달 묶음의 크기이며 전체 질문·라운드 제한이 아니다. 공식 제한이 없다면 키트도 상한을 추가하지 않는다. 실제 남은 시간 안에서 새 업무 정보·예외·성공 기준을 얻을 질문을 이어간다. 자료에 이미 명확한 조건은 근거를 확인한 뒤 짧은 계획으로 구현한다. 질문 수나 특정 경과 시간을 채우려고 기다리지 않는다.

## 답변 한 라운드의 응답 형식

```text
[이번 답변으로 확인된 사실과 근거]
[개발자에게 맡긴 범위와 우리가 정한 선택·D, 해당할 때만]
[아직 모르는 사항과 구현에 미치는 영향]
[담당자에게 보낼 다음 질문 1~3개]
[지금 구현할 수 있는 범위]
```

질문마다 답에 따라 바뀌는 동작·우선순위·검증 기준을 한 줄로 설명한다. 고객에게 기술 스택을 결정하게 하거나, 참가자에게 모르는 업무 사실을 결정하라고 묻지 않는다. 추천 업무 답변에 ‘네’라고 동의하도록 유도하지 않는다.

추가 질문이 없다면 빈 칸으로 끝내지 않는다. **어떤 근거로 현재 범위를 구현할 수 있는지**, 남은 미확인이 왜 그 범위를 뒤집지 않는지 설명한다.

새 정보가 없는 같은 쟁점은 실제 사례 하나로 좁혀 묻는다. 그래도 답을 얻지 못하면 그 규칙에 의존하는 부분만 보류·표시하고 독립 작업을 진행한다. 새 근거나 다른 사례로 확인할 수 있을 때 다시 질문한다. 아래의 명시적 위임은 답변 대기와 구분한다. 반복 답변이나 시간 부족을 정책 확정으로 취급하지 않는다. 담당자가 여럿이면 질문의 전달 대상과 답에 따라 바뀔 작업을 함께 적는다.

## 고객이 정한 것과 개발자에게 맡긴 것

| 받은 답변의 뜻 | 다음 행동 | 기존 기록에 남길 내용 |
| --- | --- | --- |
| 고객이 원하는 결과·업무 기준을 설명함 | 그 조건을 구현하고 실제로 검사한다. | Q 근거와 관련 R·수락 조건 |
| 특정 방법이나 정책을 개발자가 정하도록 명시함 | 맡긴 범위와 제약 안에서 Codex가 선택하고 구현한다. 같은 선택의 재승인을 요구하지 않는다. | 위임 근거 Q → 범위·제약·실제 선택 주체·이유·고려한 대안·한계 D → 구현·검증 |
| 답을 못 받았거나 위임 범위·필요한 업무 결과가 불명확함 | 기술 방법 대신 실제 입력·원하는 결과·금지 조건을 묻고 의존 부분만 보류한다. | 남은 질문과 영향받는 R·독립 진행 범위 |

‘그건 개발자가 개발할 부분’은 실제 질문의 범위에 맞춰 해석한다. 예를 들어 **가상 상황**에서 저장 기술을 물었더니 개발자 판단이라고 답했다면 저장 방법을 선택한다. 이를 기록 삭제나 보존 기간도 마음대로 정하라는 뜻으로 확대하지 않는다. 필요한 업무 결과가 아직 불명확할 때만 ‘다시 접속해도 이전 결과가 남아 있어야 하나요?’처럼 결과를 확인한다. 업무 정책 자체를 명확히 맡긴 경우도 기존 필수조건과 제약 안에서 선택하고 D로 기록한다.

R에는 고객이 확인한 목표·제약과 위임 범위의 근거를 유지한다. 우리가 선택한 정책은 D를 참조해 ‘개발자 선택’으로 표시하며 관련 수락 조건에서도 출처를 구분한다. 선택했다는 이유만으로 ‘고객이 이 정책을 요청/승인했다’거나 Verified라고 쓰지 않는다. 위임됐다는 이유로 계속 미확인·Blocked에 두지도 않는다. 새 상태·위임 장부·승인 절차를 만들지 않는다.

## 구현에 들어갈 조건

선택한 첫 흐름의 입력·처리·결과·수락 기준이 근거와 연결돼 있고, 여섯 영역에서 그 흐름을 바꿀 중요한 미확인이 남아 있는지 점검한다.

기존 장부의 ‘구현 진입 판단’에 **구현 가능 / 추가 질문 필요 / 부분 구현 가능**과 대상 R·근거·남은 위험·다음 행동만 간결히 적는다. 목표와 흐름의 시작/끝, 대표 입력/결과, 실제 성공·실패 검사 기준을 설명할 수 있으면 첫 흐름부터 진행한다. 관문은 Codex의 근거 있는 판단이며 매 기능에 참가자 승인을 요구하는 단계가 아니다.

- 판단 대상, 상태 변경, 권한, 기록 보존, 중요한 실패 처리처럼 답에 따라 동작이 달라지는 업무 미확인은 질문한다. 명확히 위임받은 부분은 위 범위·제약과 D를 근거로 구현하며, 그 밖의 미확인은 사실로 확정하지 않는다. 그와 무관한 작은 부분은 먼저 구현할 수 있다.
- ‘첫 사례를 들었다’ 또는 ‘수락 기준 하나가 있다’는 이유만으로 탐색을 종료하지 않는다. 한 사례를 모든 업무의 공통 규칙으로 확대하지 않는다.
- 기능 필요 여부와 우선순위를 따로 기록한다. 고객의 ‘있으면 편하다’는 답변을 바로 P0로 올리지 않는다. P0는 고객이 밝힌 필수조건 또는 확인된 성공 기준에 직접 필요한 이유가 있어야 한다. 그렇지 않으면 우선순위를 미확인으로 둔다.
- 기술 선택과 되돌리기 쉬운 세부 구현은 Codex가 진행한다. 사소한 패키지·화면 문구·색상마다 고객 인터뷰를 열지 않는다.
- MVP는 먼저 완성할 작은 흐름이다. 공식 필수 요구를 최종 범위에서 임의 제외하는 근거가 아니며, 시간 부족으로 못 마친 필수 요구는 미완료로 남긴다. 근거의 확실성·범위·진행 상태를 섞지 않는다.
- 답을 못 받은 경우 안전한 축소 범위와 미확인을 남긴다. 가설을 사실로 바꾸지 않는다. 참가자가 인터뷰를 중단하라고 하면 그 의사를 따르되, 확인된 범위와 남은 한계를 분명히 한다.

`$implement` 요청을 받아도 관련 업무 규칙의 미확인과 명시적 위임을 먼저 구분한다. 위임받은 범위는 D를 남기고 진행한다. 답을 얻지 못한 중요한 규칙은 전달할 질문을 제안하고, 독립적으로 진행 가능한 작업을 구분한다. 사용자에게 일괄적인 허가를 반복 요청하는 절차로 만들지 않는다.

## 구현 중 고객 확인

다음 두 시점에는 고객 피드백을 받을 질문을 제안한다. 기본 확인 시점이며 추가 질문 횟수를 제한하지 않는다. 같은 내용을 이미 확인했다면 근거를 남기고 반복을 생략한다.

이 확인은 참가자가 고객에게 전달하는 **업무 흐름의 설명과 질문**이다. 참가자의 중간 클릭 테스트를 뜻하지 않는다. 프로그램 동작의 중간 검증은 Codex가 AUTOMATED_TESTING.md에 따라 수행하고 실제 UI 확인은 최종 단계로 모은다.

1. **첫 작동 흐름 완성 후**: 구현한 입력 → 판단 → 행동 → 기록을 업무 언어로 짧게 설명하고, 빠지거나 다른 단계가 있는지 묻는다. 보지 않은 화면을 고객이 확인했다고 가정하지 않는다.
2. **제출 전 범위 확정 때**: 확인된 필수조건·후순위·미확인을 대조하고, 고객이 설명한 성공 기준으로 실제 사례를 처리할 수 있는지 확인한다. 실제 마감까지 자동 회귀 검사·최종 UI·복습·직접 제출을 마칠 시간이 남도록 시점을 정한다. 재개한 세션에서 초기 인터뷰 시간을 다시 채우지 않는다.

예시: ‘제가 이해한 처리 흐름은 다음과 같습니다. 실제 한 건을 이 순서로 처리할 때 빠지는 단계나 다른 부분을 알려주세요.’ 단순한 ‘이대로면 되죠?’로 확인을 대체하지 않는다.

고객에게 설명할 때 고객이 정한 조건과 개발자가 선택한 방식을 구분한다. 흐름·예시 결과·예외가 업무에 맞는지 묻고, 답변으로 달라진 R/D를 갱신한다. 고객이 설명에 동의해도 실제 앱을 실행하거나 화면을 확인했다는 근거로 쓰지 않는다. 실제 동작은 Codex의 자동 검사와 참가자가 관찰한 최종 UI 결과로 따로 확인한다.

새 판단 규칙·예외·상태 변경을 구현하다 고객 의존적 불확실성이 나타나면 두 시점 사이에도 질문한다. 질문하고 답을 받기 전에 ‘고객 확인 완료’로 표시하지 않는다.

새 답변·모순·누락된 필수 예외·실제 제약으로 의미나 범위가 바뀌면 같은 요약과 관련 R을 갱신한다. 고객/공식 확인 변경, 자체 기술 선택 D, 아직 확인할 업무 변경을 구분한다. R번호·기존 실행 이력은 유지하고 바뀐 수락 조건·근거에 영향받는 구현/검증만 다시 확인한다. 요약 문구만 바꿔 실제 규칙 변경이나 미완료를 숨기지 않는다.

## 마무리와 회고

테스트 통과와 고객 요구 탐색을 따로 확인한다. 구현되지 않은 확인된 요구, 질문하지 않은 영역, 답을 못 받은 규칙을 각각 구분하고 문답의 한계에도 반영한다.

회고에서는 질문·라운드 수를 기록할 수 있지만 그 수를 목표나 점수로 삼지 않는다. 질문으로 달라진 구현 결정, 미확인을 가정으로 확정한 사례, 종료 후 발견한 필수 요구의 누락을 살펴본다. 이 절차는 공식 배점이나 숨은 요구사항 목록이 아니다.
