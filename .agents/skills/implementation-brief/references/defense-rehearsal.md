# 답을 보지 않는 5문항 리허설

참가자가 **“Q&A 리허설 시작”**이라고 할 때 읽는다. 사전 연습 절차이며 실제 출제·공식 점수·문항 적중을 보장하지 않는다. 실제 AI 금지 평가 중이거나 제출물 확정 뒤 AI 중단 규칙이 적용 중이면 리허설·답안 생성·채점·학습 자료 열람을 돕지 않고 참가자가 직접 응시하도록 한다. 공식 시간·문항 수·자료 열람 규칙이 우선이다.

1. 공식 과제 README, 현재 코드, 기존 요구사항 정본, 공개 가능한 고객 근거 요약, 결정 기록 D/ADR, 실제 테스트·실행 기록, `docs/DEFENSE.md`와 Git 변경사항을 읽는다. `review-scope`로 커밋·스테이징·미스테이징·미추적·삭제 범위를 확인하고 실제 파일을 대조한다. Git이 없으면 그 한계를 적고 파일로 확인한다. 기존 문답의 답변을 그대로 정답으로 삼지 않는다. 테스트를 새로 실행하지 않았다면 과거 실행임을 구분한다. 기존 DEFENSE 내용은 보존하며, 양식이나 이 절차가 없더라도 이 참조의 규칙을 적용한다.
2. 아래 다섯 관점을 중심으로 **구현에 특화된 예상 질문 5개**를 만든다. 실제 함수·입력 경계·상태 전이·자체 결정·근거가 부족한 조건을 지목한다. 구현하지 않은 기능이 존재한다는 전제를 넣지 않는다. 코파프로브 평가자 역할로 연습하되 질문은 비개발자도 읽을 수 있는 쉬운 문장으로 쓴다. 필요한 함수명은 역할을 쉬운 말로 함께 지목하되 답을 드러내지 않는다.

   | 관점 | 질문에서 확인할 내용 |
   | --- | --- |
   | 전체 구조와 동작 흐름 | 사용자의 입력이 어떤 처리·저장을 거쳐 결과가 되는지 |
   | 예외 상황과 오류 처리 | 잘못된 입력·중복·중단이 생기면 실제로 어떻게 처리하는지 |
   | 스스로 정한 처리 방식 | 고객 확인과 자체 선택을 구분하고 왜 그 방식을 택했는지 |
   | 테스트와 확인 근거 | 어떤 실행으로 요구를 확인했고 어디까지 확인하지 못했는지 |
   | 한계와 개선 | 아직 부족하거나 확인하지 못한 조건과 먼저 고칠 부분 |

3. **첫 응답에는 번호를 붙인 질문 5개와 답변 방법만 보여주고 참가자의 답변을 기다린다.** 정답·힌트·기대 키워드·해설·학습 파일을 먼저 표시하거나 `LAST_REVIEW.md`를 먼저 읽게 하지 않는다. 참가자가 문서와 AI 도움 없이 자기 말로 1~5번에 답하게 한다. 코드 위치를 지목할 수 있지만 답을 드러내는 인용은 붙이지 않는다.
4. 답변을 받은 뒤 코드·테스트·현재 근거와 대조한다. 기본은 5개 답변 후 평가이며 참가자가 먼저 평가를 요청하면 답한 문항만 평가한다. 미응답은 대기로 남기고 다른 문항의 정답을 노출하지 않는다. 문항마다 **맞게 설명한 부분(정확성), 빠진 부분(누락), 다르게 이해한 부분(잘못된 가정)**을 쉬운 말로 알려주고, 뒤에 실제 경로:행·함수·실행 ID와 보충 학습 위치를 붙인다. 전문용어 암기보다 실제 동작·선택 이유·검증 범위를 이해했는지 판단한다. 근거 없는 정답이나 결정 이유를 만들지 말고 모르는 부분은 미확인으로 둔다.
5. 참가자의 실제 답변과 피드백만 Git 제외 영역 `.hackathon/study/DEFENSE_REHEARSALS.md`에 회차·검토 시점·현재 `fingerprint` 값·관련 실행 ID와 함께 간결히 보존한다. 자료를 보며 답했다면 보조받은 연습으로 표시한다. 새 질문을 제시하거나 문서를 생성한 것만으로 이해 완료라고 기록하지 않는다. 코드·요구·실행 근거가 바뀌면 관련 평가의 최신성을 재검토한다.
6. 필요하면 피드백 뒤 새 질문 5개로 다시 연습한다. 틀린 부분을 다른 입력·변경 조건으로 확인하고 질문 암기만 반복하지 않는다. 매 회차도 질문을 먼저 보여주고 답변을 기다린다.

## 보충 학습(답변 후)

실제 답변에서 이해가 막힌 흐름만 선택한다. 기본은 5문항 답변 뒤이며 먼저 평가를 요청받은 문항은 그 범위만 다룬다. 남은 문항의 정답을 노출하는 설명은 해당 답변을 받은 뒤로 미룬다.

1. 기존 고객 근거·제품 테스트·실행 기록에서 같은 실제 입력 한 건을 고른다. 업무 규칙이나 중간값을 새로 꾸미지 않는다. 민감한 값은 필요한 최소 범위로 다루며 실제 원문은 공개 문서에 복사하지 않는다.
2. **입력값 → 검사 → 처리 → 저장/응답 → 결과** 중 실제 존재하는 3~5단계를 쉬운 말로 설명하고, 각 단계의 값 변화와 실제 경로:행·함수를 연결한다. 해당 단계가 없으면 없다고 설명한다. 실제 실행에서 본 값은 check/manual ID, 코드만 읽어 따라간 값은 ‘코드 해석·미관측’, 알 수 없는 값은 ‘미확인’으로 표시한다.
3. 기존 실행 근거를 재사용한다. 새 관찰이 꼭 필요할 때만 해당 검사를 수행하고 새 ID를 연결한다. 설명을 위해 제품 코드를 리팩터링하거나 입력·정답을 맞춰 고치지 않는다. 중요한 이유는 D의 실제 결정 주체·당시 이유를 확인하고, 기록이 없으면 없다고 말한다.
4. 설명 뒤 안전한 다른 입력/변경 조건을 제시해 참가자가 자기 말로 처리 과정과 결과를 예측하게 하고 **답변을 기다린다**. 그 답변을 코드·기준과 대조한 후에만 해당 이해의 변화와 남은 오해를 기록한다. 참가자 원래 답변을 AI 문장으로 바꾸거나 미응답을 이해 완료로 표시하지 않는다.

같은 `.hackathon/study/DEFENSE_REHEARSALS.md`에 실제 응답·보충한 위치·재답변만 짧게 연결한다. 개발 중에는 여유가 있을 때 필요한 흐름만 제안하고, 응답 대기 중 독립 작업은 이어간다. 실제 AI 금지 평가에서는 이 보충 모드도 사용하지 않는다.

기존 `$implementation-brief`의 6개 주제 문답은 정답을 함께 보는 **복습 모드**다. 이 5문항 **리허설 모드**와 구분하고 `qa.json` 형식을 바꾸거나 별도 답안 DB를 만들지 않는다. 다섯 관점은 연습 범위이며 실제 질문은 달라질 수 있다. 사전 학습과 리허설을 허용된 시간에 마치고 실제 AI 금지 평가에서는 참가자가 직접 답한다.
